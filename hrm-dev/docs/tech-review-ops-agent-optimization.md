## 二、必改项（交原作者修订）

### 必改项 1：§3.C「发布方式」修正命令与 `deploy.md` 冲突且无源
- **问题**：§3.C 将发布方式修正为 `git -C /data/www/kdyzzhxt pull → cd courier-server → docker compose up -d --build`（`ops-agent-optimization.md:62`）。
- **为什么是问题**：与既有契约冲突且未声明处置——`deploy.md:101` 明确「`docker compose up -d` 会自动加载 `docker-compose.override.yml`（dev profile），**现网必须显式 `-f docker-compose.yml`**」；方案命令不带 `-f`。且全仓库无「courier-server 发布流程」记载（`deploy/deploy-demo.sh:56` 的 `docker compose up -d --build` 属演示栈，其 `:3/:76` 明示与现网独立）。触发分级红线。
- **验收标准**：该行明确写出含 `-f docker-compose.yml` 的现网发布命令；若 courier-server 发布流程在仓库内确无出处，须改为「**未验证 / 待主智能体 SSH 只读核实**」并附核实命令（如 `docker inspect courier-nginx`、`docker compose ls`），不得写成既定事实。
- **复核方式**：读方案 §3.C 该行，与 `deploy.md:101` 及 `deploy/deploy-demo.sh:3,56,76` 比对；全仓库检索确认 courier-server 发布流程来源。

### 必改项 2：§1 成因 4「SSL 五层链 / acme.sh 续期 hook」无源
- **问题**：`ops-agent-optimization.md:19` 以 `deploy.md` §79–§103 为证据主张存在「SSL 五层链」「acme.sh 自定义续期 hook」，但 `deploy.md:79-103` 仅含宿主 MySQL、数据盘分工、hids 轮转，不含该内容；§3.A A4（`:48`）沿用了该未证实链路「叶子→YE1→Root YE→ISRG Root X2→ISRG Root X1」。
- **为什么是问题**：无源结论（核心原则 1 反幻觉；tech-evaluation 维度 1 与分级红线「无源结论 → 最低打回」）。
- **验收标准**：为该两项补仓库内可查的出处（文件+行号）；若无，改为「**未验证，待 SSH 只读核实**」并给出核实命令（如 `docker exec courier-nginx nginx -T`、`ls -l /data/ssl`），A4 的链路取值同步标注未验证。
- **复核方式**：按方案给出的出处逐条核对文件是否真含该内容；否则必须以「未验证」表述。

### 必改项 3：§6 对 `agent-team-design.md` 的章节号错误

### 必改项 4：§6 遗漏 `agent-team-design.md` §5 产物契约台账同步

### 必改项 5：§3.C Nginx 修正遗漏「单文件 bind mount 原地改写保 inode」现网硬坑
- **问题**：§3.C 仅写「ro 挂载；改前备份 `nginx.conf.<时间戳>`」（`:63`）。
- **为什么是问题**：漏关键已知陷阱——`deploy.md:1059-1067` 明示「单文件绑定挂载，用 `mv`/`cp` 换文件会换掉 inode，容器仍指向旧 inode → **改动看不到**」；照 §3.C 执行将使「修正脱节」目标落空。属维度 4/5 的已知陷阱缺登记。
- **验收标准**：§3.C Nginx 行或 §3.D 操作清单补入「**原地 `cat > nginx.conf` 覆盖，禁止 `mv`/`cp` 换文件**」，并统一备份命名 `nginx.conf.<YYYYMMDDHHMMSS>`。
- **复核方式**：读方案该行与 `deploy.md:1059-1067` 比对。

### 必改项 6：H3 假设「courier-server + docker compose 为唯一部署路径」证据不足
- **问题**：§5 H3（`:91`）以 `deploy.md` §11 与 §1045 断言「唯一部署路径」。
- **为什么是问题**：依据与结论不匹配——§11/§1045 讲 Nginx 配置载体与三端入口，未涉后端运行时；`deploy.md:41-51`、`:484-553` 仍把 jar + `deploy.sh` 记为现行 D03 流程，§11 未声明其退役。据此把 jar/systemd 判为「历史方案，现网未使用」（§3.C 末行 `:66`）属未证实断言。
- **验收标准**：为 H3 补充覆盖「后端运行时」的仓库内出处；如确无，§3.C 末行「现网未使用」改为「仓库内未见记载，**待主智能体 SSH 只读核实**」并附核实命令，保留 jar/systemd 段落并加「未验证」标注。
- **复核方式**：读 §5 H3、§3.C 末行，与 `deploy.md:41-51,484-553,1022-1047` 对照。

### 必改项 7：V2 验收标准与 H1 阈值待确认存在不可判定冲突
- **问题**：§2 V2 要求「巡检清单 6 项齐全，每项含命令/阈值/异常处置建议」（`:32`），而 §5 H1 阈值「待用户确认、先按暂定值落地」（`:89`）。
