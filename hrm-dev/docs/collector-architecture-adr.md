## 2. 背景与目标

### 2.1 背景

| 项 | 内容 |
| ---- | ---- |
| 一期已完成能力 | JWT + Redis 会话认证、员工/部门/驿站管理、`station.code`（二期对接键，格式 `^[A-Za-z0-9_-]{2,50}$`）、`employee.station_id`（数据归属基础，已建 `idx_employee_station_id`） |
| 二期目标 | 自动采集驿站包裹数据 → 入库 → 站长（STATION_ADMIN）/ 管理员在系统内查询与统计 |
| 目标系统 | 多多买菜门店端：页面域 `mdkd.pinduoduo.com`，接口域 `mdkd-api.pinduoduo.com`（入口营销页 `mcmd.pinduoduo.com` 无采集价值） |
| 部署形态（用户已确认） | 采集端**集中部署在一台 Win10 / Windows 服务器**，非每驿站一台 |
| 采集账号（用户已确认） | **各驿站站长自有账号** |

> ⚠️ 目标系统与 `ddmc.pinduoduo.com/sms`（多多买菜**服务站**系统，2022-03-31 起禁用浏览器访问、仅提供 Windows 工作台客户端）是**两套不同系统**，后者非本项目目标，不得混淆。

### 2.2 触发本 ADR 的关键事实

1. **实测单驿站存量 = 133,965 条**（筛选全空、`retentionDays=0` 下取得），而非规划中「约 20 万包裹量级」这一口径模糊的表述。
2. 用户已确认**长期要做千万级包裹存量** → `plan.md` §3.1「约 20 万包裹量级」、§3.3「20 万行单表 MySQL 可承载，不提前分表」、`db.md` §1.2「二期包裹表（20 万行级）单表自增完全够用」**均已失效**。
3. 目标接口**不是裸 HTTP 可复用**：请求头含 `anti-content`（拼多多系风控签名，数百字符不透明）+ `etag` / `pdd-id`（32 位 token），且红线禁止逆向与伪造。
4. 页面为**纯 CSR 重前端**（首屏 JS ≈4.62MB、CSS ≈1.19MB、DOM 2481），且 **URL 不承载状态**（history 路由，筛选状态仅在 SPA 内存）→ 不能拼 URL 复现筛选，必须复现请求体。
5. DOM 中**业务语义 `data-*` 几乎不存在**（仅行级 `data-row-key` 且为序号）→ DOM 抓取路线天然脆弱。
6. ~~`retentionDays` **疑似平台留存窗口**（推断 ≈4~5 个月）→ 漏采即永久缺口。~~ ⚠️ **2026-09-19 实测推翻**：`retentionDays` 经 bundle 静态分析确认是**「滞留天数」筛选条件**（包裹在站内的滞留天数，同时是表格列与响应字段），**与平台留存窗口无关**。原推断作废，K1 降级并改写（见第 11 章与第 17 章）。
7. **增量同步的窗口参数已确认存在**（第 17 章）：请求体含 5 组日期区间（`arriveTime` / `departTime` / `deliveryTime` / `inCabinetTime` / `signTime`），**当前 ADR-C09 的「兜底全量轮扫先行」不再是唯一可行路径**。

## 3. 架构约束矩阵

### 3.1 业务约束

| 编号 | 约束 | 来源 | 架构含义 |
| ---- | ---- | ---- | ---- |
| B1 | 单驿站存量 133,965 条 | 实测 | 首灌必须一次做全；分页通道至少 2680 次请求 |
| B2 | 长期千万级包裹存量 | 用户确认 | 必须做分区/分表 + 冷热分离 + 归档；原「20 万单表」结论作废 |
| B3 | 采集端集中一台 Win10/服务器 | 用户确认 | 单机承载多驿站、多账号、多浏览器上下文；需进程级隔离与队列复用 |
| B4 | 各驿站站长自有账号 | 用户确认 | 登录态与账号强绑定；账号健康度、失效人工介入成为常态运维项 |
| B5 | **漏采即永久缺口** | 推断（依赖 V3） | 必须有连续性校验 + 缺口登记 + 告警制度，不能只写进风险表 |
| B6 | 一期依赖不变 | plan.md §3.4 | `station.code` 冻结、`employee.station_id` 复用、`hrm:` / `crawler:` Redis 前缀隔离 |
| B7 | 不启用「运单导入」反向写入 | collector-site-analysis.md §2 | 采集端**只读**，不回写平台，规避写操作合规风险 |
| B8 | 站长需看本站数据 | requirement.md §3.1 / plan.md §3.2 | 启用 `STATION_ADMIN`，可见范围按 `employee.station_id` 收口 |

### 3.2 技术约束

| 编号 | 约束 | 来源 | 架构含义 |
| ---- | ---- | ---- | ---- |
| T1 | 主数据接口服务端分页、50 条/页、无跳页输入框 | 实测 | 只能顺序翻页；2680 页必须由队列 + 断点承接 |
| T2 | 单次 `query_waybill` 644ms | 实测 | 首灌时长由「间隔下限」主导，非由响应耗时主导 |
| T3 | `anti-content` / `etag` / `pdd-id` 参与校验 | 实测 | 排除自造请求；只能借道页面自身请求 |
| T4 | 页面纯 CSR，JS 4.62MB / CSS 1.19MB / DOM 2481 | 实测 | 浏览器渲染成本高 → 页面实例必须常驻复用，禁止每页重开 |
| T5 | URL 不承载状态，筛选只在内存 | 实测 | 无法用 URL 复现筛选；必须驱动页面自身发请求 |
| T6 | `data-*` 缺失，定位靠 class + 列序/列名 | 实测 | DOM 依赖脆弱 → 只作「触发器 + 状态观测」，真值以接口响应为准 |
| T7 | 全量 133,965 条 = 2680 页 | 实测（133965÷50） | 首灌与全量兜底轮扫的规模基线 |
| T8 | 双库 MySQL 8 + PostgreSQL 同步维护 | db.md §1.5 | 分区/分表方案须写明双库差异，不接受仅 MySQL 可用的方案直上 |
| T9 | 生产只拉 Git 代码、宝塔部署 | 项目规则 §4 | 采集端升级走版本化产物 + 服务端下发配置，禁止服务器手改 |
| T10 | 采集端运行于 Windows | 用户确认 | 需 Windows 服务/托盘、远程协助通道、浏览器版本锁定 |

### 3.3 合规约束（硬红线，不可协商）

| 编号 | 红线 | 落地要求 |
| ---- | ---- | ---- |
| C1 | 仅采集**自有账号、自有驿站**数据，不跨机构越权 | 账号 ↔ 驿站一对一绑定并校验；机构列表只取自有授权项 |
| C2 | **限速 + 熔断**：串行请求、请求间隔下限、并发 = 1；命中验证码 / 403 / 429 / 跳登录 / 结构突变即**立即终止并出报告** | 限速熔断层为强制经过路径，熔断后**禁止自动重试绕过** |
| C3 | **不做反检测伪装**：不轮换 UA、不用代理/IP 轮换、不注入脚本对抗指纹、**不伪造或逆向 `anti-content`** | 技术选型中显式排除相关库（Crawlee proxy rotation、undetected-chromedriver、puppeteer-stealth 等） |
| C4 | 遵守 robots.txt 与站点爬取延迟声明 | 采集前读取并记录 robots 声明与站点使用条款快照（存档于服务器本地，不入 Git） |
| C5 | 真实业务数据（运单号 / 收件人 / 手机号 / 地址）不落 Git，按 db.md 规范脱敏存放 | 采集端日志脱敏、异常堆栈不打印响应体；Git 内仅占位符 |

### 3.4 资源约束

| 编号 | 约束 | 架构含义 |
| ---- | ---- | ---- |
| R1 | 开发机无 JDK/MySQL/Redis（requirement.md §1.3） | 本阶段只交付设计；编译/运行验证集中在部署阶段 |
| R2 | 仅一台采集设备 | 多账号 ↔ 多浏览器上下文的资源上限需量化（内存/句柄/端口） |
| R3 | 不引入代理/IP 池（红线 C3） | 无代理成本，但**时长成本不可压缩**，必须用队列与断点换取容忍度 |
| R4 | 不引入重型分布式中间件 | 单机 + 服务端单体即可；不引入消息队列/K8s |

## 4. 非功能需求（NFR）

> 下列均为**设计目标**（非实测值）；实测基线见第 5 章。

| 维度 | 指标 | 目标 | 依据 / 备注 |
| ---- | ---- | ---- | ---- |
| 性能 | 单站首灌（133,965 条）时长 | 模型值 **≈2.7 小时/站**（2680 × (0.644s + 3s) ≈ 9766s）；排期按 **3~5 小时**留缓冲 | 间隔下限取值见 ADR-C14（取值本身待 robots 核查，见 V8） |
| 性能 | 日常增量（窗口增量路径） | ≤ 5 分钟/站/日 | 20~40 页/日；**推断**，依赖筛选映射验证（V1） |
| 性能 | 日常增量（全量轮扫兜底路径） | ≈3~5 小时/站/日 | **不具可扩展性**：单机串行日预算约 ≤20 小时 → 该路径最多支撑 4~6 个站点；超出即当日无法闭合（详见 8.2 与 V9） |
| 性能 | **单机日时间预算（硬约束）** | 可用采集时长 ≤ 20 小时/日（24h 扣运维/告警/补采窗口） | 决定集中单机可承载的**站点数上限**；并发被红线 C2 固定为 1，无法用并发换时间 |
| 性能 | 包裹列表查询 P95 | < 500ms（单站 ≤ 200 万行） | 对齐 requirement.md §6.2；靠 `(station_id, status, time)` 复合索引；单站规模与站点数的组合口径待容量评估（V9） |
| 性能 | 包裹回推接口 | 单批 ≤ 500 条/次，P95 < 2s | 拟，控制单次事务体积 |
| 可用性 | 采集窗口闭合率 | **100%**（硬指标） | 漏采即永久缺口（B5）；未闭合必须登记缺口并告警 |
| 可用性 | 采集端 daemon 连续运行 | ≥ 7×24，单次崩溃自愈 < 60s | 常驻进程 + 看护重启 |
| 可用性 | 熔断后人工介入时长 | < 4 小时（工作时间内） | 决定最大缺口窗口；与增量回扫窗口联动 |
| 安全 | 平台凭据落地 | 仅采集端本地加密文件，**服务端零留存** | 见第 10 章 |
| 安全 | 出参脱敏 | 手机号全量字段不出 JSON | 对齐 api.md §1.4 |
| 可扩展性 | 新增一个平台适配器 | 仅新增适配器实现 + 服务端配置，**不动**队列/限速/落库层；**注意：新增平台需采集端发版**（Review 修订，见 K17 / ADR-C15/C16） | ADR-C16 |
| 可扩展性 | 数据规模 | 支撑 10^7 行、站点数 ≤ 100 不重建表 | ADR-C11 |
| 可维护性 | 采集端配置变更 | 服务端下发，**不发版** | ADR-C15 |
| 可维护性 | 本地日志留存 | 滚动 30 天 + 脱敏 | 不含响应体明文 |
| 可观测性 | 心跳周期 | 30s；连续 3 次缺失判定离线 | 拟（ADR-C19） |

### 5.2 风控与登录态

| 项 | 实测值 | 架构含义 |
| ---- | ---- | ---- |
| `anti-content` | 请求头，数百字符不透明签名 | **不逆向、不伪造** → 排除路线 D |
| `etag` / `pdd-id` | 两个 32 位不透明 token | 与设备/会话绑定 → 排除「拷贝请求头另开 HTTP 客户端」的做法 |
| `p-appname` | `DDStore-PC` | 同上 |
| 风控埋点 | `POST xg.pinduoduo.com/xg/pfb/a2`（≈11 次） | 只读观察，不触碰 |
| 隐藏 iframe | `BODY#watermark` 下 1 个视口外 `x=-10000`、`src` 空的 iframe | 疑似指纹/埋点帧；**不注入脚本对抗** |
| Cookie / UA / Referer / Origin | **未获取**（页面内不可见）→ 未验证 | 路线 C 依赖浏览器自动携带，天然规避 |
| 登录态有效期 | 本轮全程未登出、未触发验证码 → **未验证** | 待验证 V4 |

### 5.3 页面与交互

| 项 | 实测值 | 架构含义 |
| ---- | ---- | ---- |
| 技术栈 | React + single-spa 微前端 + Rocket UI + 自研 `station` 组件（无 antd） | 重前端，页面实例须常驻 |
| 首屏体积 | JS ≈4.62MB、CSS ≈1.19MB（解码） | 单页打开成本高，禁止逐页重建 |
| DOM 节点 | 2481（`#root` 子树 2318） | 同上 |
| 表格结构 | 表头/表体双 `table`；表体第 1 行为隐藏测量行 `tr.rocket-table-measure-row` | DOM 解析必须排除测量行 |
| 行标识 | `data-row-key`（**序号，非业务主键**） | 无业务锚点，行 ↔ 数据映射不可靠 |
| 列 | 可见列名 17 列，`thead th` 计数 18（差异**不确定**） | 取数须按**列名文本匹配**，不得按索引 |
| 分页 | 每页 50；**无跳页输入框**；有上一页/下一页与页码按钮 | 只能顺序翻页 |
| 筛选 | 16 个条件，默认全空；默认即全量 133,965 条 | 可实现「全量轮扫」兜底（入参已实测） |
| URL | 点击查询/翻页后 **URL 不变** | 状态只在内存 |
| 演示入口 | `div.table-menu` 内「导出Excel」→ 结果落 作业中心/下载任务 `/vw/operationCenter/download` | 见 5.4 |
| 实测样本任务 | 任务名「包裹明细导出」、状态「已失效」、创建与失效相隔约 1 天 | 导出件≈1 天有效 |
| 负向观察 | 菜单内**无**独立入库/取件/到货/出库入口，**无**独立「订单」入口（仅菜单层面结论） | 包裹状态只能从运单查询/接口取 |

| 结果容器 | 下载任务页（列：任务名称/状态/创建时间/失效时间/操作人/操作） |
| 下载入口 | 行内 `button.rocket-btn.rocket-btn-link`（失效行 disabled） |
| 新建入口 | 下载任务页**本身无新建入口**，任务只能从运单查询页发起 |
| 导出接口 / 文件格式 / 条数上限 / 频次限制 / 是否受筛选影响 / 字段完整度 | **全部未验证** |

### 5.5 与决策无关的事实（明确排除）

- 入口营销页 `mcmd.pinduoduo.com`（Next.js SSR，`__NEXT_DATA__`）：无采集价值，不纳入取数域。
- 站点自身埋点报错（`apm.pinduoduo.com/*` → `net::ERR_ABORTED`）：站点原有行为，与采集无关。
- 响应式六档尺寸：本自动化环境无视口控制能力，**未实测**；该维度不影响采集端架构（采集端使用固定大视口）。

## 6. 取数路线选型对比

### 6.1 路线定义

| 路线 | 定义 |
| ---- | ---- |
| **A. 平台原生导出** | 运单查询页 → 「导出Excel」→ 下载任务页取件 → 解析文件入库。**不触碰 `anti-content`** |
| **B. 开放平台 API** | `open.pinduoduo.com` 运单/物流类 API + 驿站账号授权 |
| **C. 页面上下文内响应监听** | 借道页面**自身**发起 `query_waybill`（点击查询/翻页触发），采集端在页面上下文内**旁路读取响应**；不构造请求、不接触签名 |
| **D. 自行构造请求并逆向 `anti-content`** | 自造 HTTP 请求 + 破解签名生成 |

### 6.2 对比

| 维度 | A 原生导出 | B 开放平台 API | C 页面上下文内响应监听 | D 自造请求 + 逆向签名 |
| ---- | ---- | ---- | ---- | ---- |
| 实测可行性 | **未验证**（导出接口/格式/上限/频次全未知） | **未验证**（是否有运单类 API、驿站账号能否授权未知） | **可行**：入参/分页/响应结构已实测，页面可驱动 | 理论上可行，**合规上禁止** |
| 对 `anti-content` 依赖 | **无** | 无（平台授权通道） | **无**（签名由页面自身生成，采集端不接触） | 强依赖，需持续对抗 |
| 单站首灌能力 | 潜在最优（一次导出全量；条数上限未验证） | 潜在最优 | 2680 次串行请求 | 2680 次串行请求 |
| 稳定性 | 依赖平台导出任务可用性与文件稳定性 | 依赖开放平台接口契约与授权范围 | 依赖页面 DOM（触发器脆弱）+ 接口（已验证） | 依赖签名算法不变，最脆弱 |
| 合规性 | 高（平台原生功能） | **最高**（官方授权） | 高（复用自有账号在自有页面的正常操作 + 只读旁路） | **不可接受** |
| 成本 | 中（文件解析 + 任务状态轮询） | 低（接口直连） | 中（浏览器常驻 + 队列 + 限速） | 高（持续逆向维护） |
| 缺口/断点友好度 | 中（导出件≈1 天失效，需在有效期内取件） | 高 | 高（游标分页天然可断点续传） | 高（但不可选） |
| 结论 | **首灌优先验证通道** | **并行评估，长期最优候选** | **主力通道（增量 + 首灌兜底）** | **明确排除** |

### 6.3 结论

1. **路线 D 明确排除**，理由三条，任一成立即不可行：
   1. **合规**：违反红线 C3「不伪造或逆向 `anti-content`」；也违反 C1 精神（伪造客户端身份）。
   2. **法律与条款**：绕过平台技术保护措施，存在违反站点使用条款与相关法规的风险。
   3. **工程**：签名算法不透明且会漂移，维护成本无上限，一旦失效即全线停摆。
   - 附带排除：**mitmproxy 中间人解密暂不启用**（需安装根证书做 TLS 解密，与红线 C3/C5 冲突），仅登记为**技术储备**，不进入实现路径。
   - 附带排除：Crawlee 的 proxy rotation / fingerprint 生成、undetected-chromedriver、puppeteer-stealth 等反检测库，**一律不引入**。
2. **路线 C 为主力通道**：它是唯一「已实测可行 + 不触碰签名 + 可断点续传 + 合规可辩护」的通道。首灌 2680 页、日常增量、全量兜底轮扫均走 C。
3. **路线 A 作为首灌优先验证通道**：若导出件能覆盖全量且字段完整，可把首灌从「2680 次请求」压缩为「1 次导出 + 解析」，显著降低风控暴露面与总时长。**在 V2 验证通过前，A 不得作为唯一首灌手段**，必须保留 C 兜底。
4. **路线 B 并行评估**：若开放平台存在运单/物流类 API 且驿站账号可授权，则长期应迁移至 B（最合规、最稳定）。评估不阻塞二期开工。

> 借鉴来源（只借鉴设计思路，不照搬代码）：Crawlee 的 `RequestQueue`（持久化队列 / 断点续传）与 `AutoscaledPool`（并发自适应思路，本项目受红线限制**固定并发 = 1**）；Vercel Labs agent-browser 的「CLI 控制端 + 常驻 daemon 分离」结构；BrowserForce 的「CDP 连接用户真实已登录浏览器、不自行托管登录态」思路；DBSyncer 的全量/增量任务模型与同步监控指标；抖音矩阵方案的「时间戳增量 + 单号去重」范式。

### 7.1 分层架构

### 7.2 各层职责与关键约定

| 层 | 职责 | 明确不做 |
| ---- | ---- | ---- |
| L1 控制层 | 任务编排、配置下发、落库幂等、缺口检测、告警 | 不存平台凭据、不代管登录态、不反向连入采集端 |
| L2 守护进程层 | 常驻、看护、调度、心跳、升级、日志 | 不解析业务字段（保持「薄」） |
| L3 浏览器连接层 | 连接**本方案专用、由人工登录**的浏览器实例、标签页复用、登录态探测、CDP 通道安全收口（10.2.1） | **不代管凭据、不自动登录**；不注入对抗脚本、不改 UA；不复用日常浏览器 |
| L4 采集队列层 | 游标推进、断点、批次、去重键 | 不做风控判断（交 L5）、不落库（交 L6） |
| L5 限速熔断层 | 串行、间隔下限、熔断终止 | **不提供自动绕过/重试捷径**；熔断后只能人工确认恢复 |
| L6 落库回推层 | 字段映射、脱敏、分批回推、批次结果 | 不直连业务库（只调 `/api/v1/crawler/*`） |
| L7 平台适配器层 | 平台差异化收口（路径/入参/翻页/映射/触发器） | 不含平台无关逻辑（队列/限速/回推） |

**依赖方向单向向下**：L2 → L3 → L4 → L5 → L6，L7 被 L2/L4/L6 以接口方式使用；不允许 L4~L6 直接依赖具体平台实现。

### 7.3 关键约定

| 项 | 约定 |
| ---- | ---- |
| 认证 | 服务端双体系：管理端 JWT（`Authorization: Bearer`）+ 采集端 API Key（`X-Crawler-Key`，密钥仅存服务器配置与采集端本地加密文件） |
| Redis Key | 沿用 plan.md §3.3：`crawler:lock:{station_id}`；新增拟：`crawler:task:{station_id}`、`crawler:heartbeat:{collector_id}`（均 `crawler:` 前缀，与 `hrm:` 隔离） |
| 服务端不主动连入 | 采集端出站轮询（拉模式），无公网入站要求 |
| 采集端保持「薄」 | 接口路径、入参模板、翻页规则、字段映射、限速参数全部服务端下发（ADR-C15） |
| 只读边界 | 仅调用查询类接口与页面内查询动作；**不调用任何写接口**（含运单导入） |

## 8. 关键流程设计

### 8.1 首灌全量流程

```text
服务端：为 station 生成 sync_task(full_load)
   ↓
采集端 L2 领取任务（Redis 锁 crawler:lock:{station_id}）
   ↓
L3 附着已登录浏览器 → 打开运单查询页 → probeLogin()
   ├─ 未登录/跳登录 → 熔断（C2）→ 出报告 → 任务置 failed(需人工)
   └─ 已登录 → 进入首灌
   ↓
【通道判定】依据 V2 验证结论：
   ├─ 导出通道可用 → 触发「导出Excel」→ 轮询下载任务页（任务约 1 天失效，实测样本）
   │     → 取件 → 解析 → 按 (station_id, waybill_no) 幂等 upsert → 批次留痕
   └─ 导出不可用/字段不全 → 走 C 分页：
         for pageNo = 1 .. N:
             L5.acquire()（串行 + 间隔下限）
             触发页面翻页/查询 → L3 旁路读取 query_waybill 响应
             L6.normalize → 脱敏/校验 → 分批回推
             L4.commitCursor(pageNo)（本地持久化）
             若 L5 熔断 → 保存游标 → 任务置 interrupted → 出报告
   ↓
首灌完成 → 对账（**Review 修订**：不得以 result.total 作稳定基准）
   │  原因：total 会随平台留存窗口漂移（V3 未验证），今次 133965 ≠ 下次 133965
   │  修正为「同源对账」：本轮实际扫取条数 vs 本轮落库集合大小（同一次运行内自洽）
   ├─ 差值 ≤ 阈值 → 任务置 success
   └─ 差值超阈值 → 登记缺口（sync_gap）→ 告警 → 人工确认后补采一次
   └─ （V3 确认 total 语义后，方可启用「远端 total vs 本地计数」的跨源对账，见 ADR-C18 第 3 条）
```

### 8.2 日常增量流程（双模，兜底优先落地）

```text
每日定时（低频窗口，避开平台业务高峰，具体时段待定）
   ↓
【模式 1：窗口增量】需 V1 验证通过（筛选 → 请求体映射）
   触发页面按「时间区间」筛选（覆盖上次窗口末端 + 重叠冗余）→ 分页拉取
   → 按 (station_id, waybill_no) upsert；gmtModified 更新的行执行覆盖写
   → 连续性校验：本次时间下界 ≤ 上次时间上界，否则判缺口
【模式 2：全量轮扫（兜底，已实测可行）】V1 未通过时启用
   入参固定 { siteOrgCode, retentionDays=0, pageSize=50, pageNo }（实测）
   逐页扫全量（2680 页）→ 幂等 upsert → 天然覆盖全部状态变更
   代价：每站约 2.7 小时（模型值）/ 3~5 小时（含缓冲）→ 随站点数线性增长
   ⚠️ 容量上限：单机串行日预算 ≤20 小时 → 模式 2 最多支撑 4~6 个站点
      站点数超出后无法当日闭合，直接产生 K1 缺口 → 必须降级为「周度全量对账」
      或在 V1 通过前限制启用站点数（见 ADR-C09 修订与 V9）
   ↓
批次留痕：sync_batch{batch_no, station_id, mode, 请求页数, 响应条数, 新增/更新/跳过条数, 开始/结束时间}
```

> **设计取舍**：模式 2 不依赖任何未验证假设，是唯一「今天即可落地」的增量方案；模式 1 依赖 V1，验证通过后切换以降本。两者共用同一幂等键与批次留痕，切换不动数据层。
>
> ⚠️ **主智能体 Review 修订（2026-09-19）**：原稿称模式 2「仅作过渡」，未量化其容量边界，与本 ADR 自身的两条前提冲突——① 部署形态为**集中单台**（ADR-C01）；② 并发被红线 C2 **固定为 1**。二者相乘得到硬结论：**模式 2 的日吞吐上限 = 单机日时间预算 ÷ 单站耗时 ≈ 20h ÷ 3~5h ≈ 4~6 个站点**。
> 因此模式 2 **不是**可长期托底的方案，而是**有站点数上限的过渡方案**。在 V1 未通过期间必须二选一：**(a)** 限制启用站点数在 4~6 以内；**(b)** 把全量轮扫降频为**周度对账**（不再承担日常增量职责），日常缺口靠后续 V1 补。若站点数增长而 V1 仍未通过，则该路径**直接失效**，须回到 V1 攻关，不存在第二条路。

### 8.3 导出通道流程（备选首灌通道）

```text
运单查询页 → 点击「导出Excel」（仅此页有入口，下载任务页无新建入口）
   ↓ 轮询「下载任务」页：任务状态 → 生成中 / 已完成 / 已失效（实测样本：约 1 天失效）
   ├─ 已完成 → 取件（行内下载按钮）→ 落到采集端本地受控目录
   │     → 解析（格式未验证：xlsx/csv）→ 字段完整性校验（尤其 operationList 等全量字段）
   │     → 幂等 upsert → 批次留痕 → 本地文件按脱敏规范销毁/归档（不入 Git）
   └─ 已失效 → 登记失败 → 回退路线 C 分页
风险：导出条数上限 / 频次限制 / 是否受当前筛选影响 → 均未验证（V2）
```

> ⚠️ **2026-09-19 实测补充：本流程有三处"想当然会失败"的坑，已在第 18 章给出补丁。**
> 简述（细节见 18.3）：**(1)** CDP 连上的浏览器由 Chrome 自身处理下载，Playwright 的 `page.on("download")` **不触发**，必须显式开启 `Browser.setDownloadBehavior`；**(2)** `page.goto()` 直接命中附件 URL 会抛 `Download is starting` **但文件已落盘**，必须 try/except 并改用 CDP 层 `Browser.downloadWillBegin` 兜底；**(3)** 取件必须复用人工登录态所在的 `browser.contexts[0]`，新建 context 不继承 Cookie。
> 该流程亦为**原借鉴方案的漏项**（三个开源参考均未覆盖"下载/取件"链路）。

### 8.4 熔断与恢复流程

```text
每次请求前后由 L5 采集信号：
   ├─ 正常 → 记录 RTT、状态码 → 继续
   ├─ 单次异常（超时/5xx）→ 重试上限 2 次（间隔递增）；仍失败 → 判定熔断
   └─ 硬熔断信号（任一命中，立即终止）：
        验证码 / 滑块、HTTP 403、HTTP 429、跳转登录页、响应结构突变（success 缺失或 result 结构变化）
   ↓
硬熔断动作（不可跳过）：
   1. 立即停止本任务全部请求；
   2. 保存游标与批次状态（先落盘，再上报）；
   3. 服务端上报熔断详情（站点、任务、批次、页码、命中信号、时间，**不含响应体明文与业务数据**）；
   4. 任务置 interrupted，缺口登记（窗口未闭合）；
   5. 生成报告，写入采集端本地 + 服务端；托盘与看板告警；
   6. **禁止自动恢复**：必须人工确认后从游标处续采。
```

## 9. 数据层设计要点（千万级）

> 本章只给**设计要点与决策**；完整 DDL 由数据库工程师专项设计（含 MySQL / PostgreSQL 双脚本）。

### 9.1 分区 / 分表路线

| 方案 | 是否满足 MySQL 硬约束 | 防重能力 | 结论 |
| ---- | ---- | ---- | ---- |
| **按 `station_id` HASH 分区**（在线主表） | ✅ 分区键 = `station_id`，唯一键含之即合法 | ✅ `(station_id, waybill_no)` 保持全局唯一 | **采纳** |
| 按时间 RANGE 分区（在线主表） | ⚠️ 唯一索引必须包含分区列 → 需补时间列进唯一键 | ❌ 降级为「同分区内唯一」 | 不采纳为在线主方案 |
| 按 `station_id` 分表（应用层路由） | ✅ | ✅ | 备选（站点数爆发或单站破千万时启用） |
| 不分区 + 纯归档表 | ✅ | ✅ | 短中期可接受，与 HASH 分区并用 |

**MySQL 硬约束说明（关键）**：MySQL 分区表要求**每个唯一索引（含主键）必须包含分区表达式的全部列**。

- 若采用**时间 RANGE 分区**（如按月），则 `(station_id, waybill_no)` 唯一键必须补一个时间列变成 `(station_id, waybill_no, <时间列>)`；结果是**同一运单在不同月份被重复采集会产生两行**，防重能力被削弱，跨分区重复只能靠业务层幂等兜底（写入前查重 + `gmtModified` 比较 + 日终对账）。
- 若采用**按 `station_id` HASH 分区**，分区键本身就在防重键内，`(station_id, waybill_no)` 唯一键**原样成立**，防重能力**不打折**。故**在线主表选 `station_id` HASH 分区**。
- **主键副作用**：分区表主键必须含 `station_id` → 主键采用 `(id, station_id)` 复合（`id` 在前，满足「自增列须为某索引首列」）。若未来改为分表/分片，再评估雪花 ID（登记为技术储备，本期不引入，避免 Long 精度序列化改造）。
- **归档表例外**：历史归档表（只写不改、不承担在线唯一约束）可按时间 RANGE 分区，便于按时间 `DROP PARTITION` 快速清理。
- **双库差异**：PostgreSQL 声明式分区同样要求唯一约束包含分区键，但 `PARTITION BY HASH` 语法与维护方式不同 → 双库脚本分别提供；若某库暂不支持，允许 PostgreSQL 侧先用「不分区 + 归档表」降级（行为一致优先于特性一致）。

### 9.2 唯一键与幂等

| 项 | 要点 |
| ---- | ---- |
| 业务防重键 | `uk_parcel_station_waybill (station_id, waybill_no)`（对齐 plan.md §3.3 / db.md §6.2） |
| 幂等语义 | `INSERT ... ON DUPLICATE KEY UPDATE`（MySQL）/ `ON CONFLICT DO UPDATE`（PG） |
| 更新判定 | 以响应中的 `gmtModified` 为准做后写覆盖（**不早于**本地值才更新），避免乱序覆盖 |
| 批次留痕 | `parcel.last_sync_batch_no` + `parcel.first_collect_time` / `last_collect_time`；批次级明细落 `sync_batch` / `sync_log` |
| 防重键与「缺口补采」冲突处理 | 补采走同一幂等键 → 天然不产生重复行 |
| 批内去重 | 回推前在采集端按 `(station_id, waybill_no)` 取 `gmtModified` 最新一条，减少无效写入 |

### 9.3 索引要点

| 索引 | 用途 |
| ---- | ---- |
| `uk_parcel_station_waybill (station_id, waybill_no)` | 防重 + 单号定位 |
| `idx_parcel_station_status_time (station_id, status, in_cabinet_time)` | 站点维度列表（主查询模式） |
| `idx_parcel_station_gmt_create (station_id, gmt_create)` | 站点维度时间排序 / 增量对账 |
| `idx_parcel_mobile_tail4 (station_id, receiver_mobile_tail4)` | 按手机号后 4 位查询 |
| `idx_parcel_batch (last_sync_batch_no)` | 批次追溯与问题定位 |

**查询纪律**（继承 plan.md §3.3）：避免 `SELECT *`；列表查询使用**游标分页 / 延迟关联**，禁止深分页 `LIMIT 大偏移`。

### 9.4 字段落地与脱敏存储（对齐红线 C5 与 api.md §1.4）

| 平台字段 | 本地落地建议 | 理由 |
| ---- | ---- | ---- |
| `trackingNumber` / `siteOrderSn` / `deliveryOrderSn` | 明文入库（不进 Git） | 业务主键，查询必需 |
| `receiverMobile` | **只存后 4 位** `receiver_mobile_tail4` | 页面查询仅支持「手机号后 4 位」（实测占位文案），全量存储无业务收益、徒增风险 |
| `receiverName` | 脱敏存储（保留姓氏 + 掩码，如 `张*`） | 查询不需要完整姓名 |
| `operationList`(string[]) | 序列化存储（TEXT/JSON 字符串，长度按需） | 操作轨迹，用于状态判定；具体长度上限**未验证** |
| `siteOrgCode` / `siteCode` | 不落业务表（仅用于请求入参） | 避免冗余机构码扩散；仅保留 `station_id` 映射 |
| 地址类字段 | 接口未出现 → 不涉及 | 实测字段清单无地址 |

> 以上为**架构建议**，最终字段口径由数据库工程师与业务确认后落 DDL。

### 9.5 冷热分离与归档

| 项 | 要点 |
| ---- | ---- |
| 热区定义 | 近 N 个月（N 待定，建议与状态流转周期对齐；`retentionDays` 若为 4~5 个月，热区取 6 个月可覆盖在线可回补范围） |
| 冷区 | `parcel_archive`（按时间 RANGE 分区，只写不改） |
| 归档触发 | 定时任务按月下沉；归档前先校验连续性（避免把缺口数据固化） |
| 查询路由 | 列表默认查热区；历史查询显式走归档表（前端需给「含历史」选项） |
| 删除策略 | **禁止物理删除业务数据**（缺口不可回补，误删不可恢复）；仅归档 |
| 与分区关系 | HASH 分区不便于按时间 `DROP PARTITION` → 时间维度的清理能力由归档表承担 |

## 10. 安全与合规设计

### 10.1 红线落地对照

| 红线 | 落地机制 | 验证方式 |
| ---- | ---- | ---- |
| C1 仅自有账号/自有驿站 | 账号 ↔ `station_id` 一对一绑定（`collect_account` 拟新增，见 10.4）；请求 `siteOrgCode` 只能取该账号自有授权项 | 越权测试：构造他人机构码 → 采集端本地拦截 + 服务端拒绝 |
| C2 限速 + 熔断 | L5 强制经过层；并发 = 1；间隔下限（ADR-C14）；硬熔断信号 5 类；熔断后禁止自动恢复 | 代码评审 + 熔断演练（注入 429/验证码场景） |
| C3 不做反检测伪装 | 不轮换 UA、不用代理/IP 池、不注入对抗脚本、不逆向 `anti-content`；依赖干净：**不引入任何 stealth / undetected / proxy-rotation 库** | 依赖清单审查（构建期检查） |
| C4 遵守 robots 与爬取延迟 | 采集前读取并留存 robots 声明与站点条款快照（存服务器本地，不入 Git）；间隔下限不低于声明值 | 首次运行前人工确认；快照存档 |
| C5 数据不落 Git、脱敏存放 | 本地日志脱敏（不打印响应体/手机号/运单号全量）；导出文件落受控目录并及时销毁；Git 仅占位符 | 提交前自检 + 仓库扫描 |

### 10.2 凭据不落地

| 项 | 约定 |
| ---- | ---- |
| 平台登录态 | **由人工在真实浏览器中完成登录**；采集端不代管账号密码、不保存密码、不自动登录 |
| 平台凭据 | 无（不采集密码）。浏览器 Cookie / `etag` / `pdd-id` 留在浏览器自身存储中，**采集端不落盘、不回传服务端** |
| 采集端 API Key | 仅存采集端本地加密文件（Windows DPAPI）+ 服务器配置；**不入 Git、不入日志、不入响应** |
| 服务端 | **零平台凭据**：不知道站长账号密码，也无法代表站长登录 |
| 加密方式 | DPAPI（Windows 本地用户级）为默认；不引入自定义加密算法（避免自研密码学） |

#### 10.2.1 CDP 附着模式的信任边界（**主智能体 Review 新增 · 高危项**）

原稿采纳了「CDP 附着人工已登录浏览器」（ADR-C05），但未定义其信任边界。该模式的安全含义是：**任何能连上该 CDP 端口的进程，都可完全接管该浏览器，读取其全部 Cookie 与 localStorage，并以已登录身份发起任意操作**。本方案的应用域不止多多买菜，若不设边界，集中机上一旦存在其他恶意/失控进程，等同于把**全部站长账号的浏览器会话**交出去。必须落以下硬约束：

| 约束 | 要求 | 理由 |
| ---- | ---- | ---- |
| **专用浏览器实例** | 必须使用**独立安装/独立 profile 的专用浏览器实例**，该实例**仅登录多多买菜门店端**，不得复用站长或运维人员的日常浏览器 | 把「可读全部站点 Cookie」的暴露面收敛到「仅多多一个站点」，而非整台机器的所有登录态 |
| **端口绑定** | CDP 端口必须绑定 `127.0.0.1`，**绝不允许监听 `0.0.0.0` / 局域网 / 公网**。⚠️ **2026-09-19 实测**：`--remote-debugging-port` **默认就只 LISTEN 在 `127.0.0.1`**，无需额外加固；风险点在于**绝不能添加 `--remote-debugging-address=0.0.0.0`**（会把浏览器直接开放出去）。该条写入**装机 checklist** 逐项核对 | 端口一旦对外，等于把已登录浏览器直接开放给同网段任何人 |
| **来源白名单** | **禁止** `--remote-allow-origins=*`；仅允许精确的本机来源（如 `http://localhost`） | 通配来源可被任意网页通过 WebSocket 劫持调试通道 |
| **专用端口** | 使用非默认/非通用端口，避免与运维工具（如通用 9222）冲突或被扫描命中 | 降低被本机其他工具误连/主动扫描的概率 |
| **专用 Windows 账户** | 浏览器实例与 daemon 运行在**专用本地账户**下，`--user-data-dir` 位于该账户私有目录并收紧 ACL | 使 profile 与 DPAPI 密钥不与其他用途共享 |
| **不安装第三方远控** | 见 ADR-C19：不强制安装 ToDesk/向日葵等第三方远控；确需远程协助须走 Windows 远程桌面/受控通道并经安全评估 | 第三方远控本身持有一切权限，会直接击穿上述边界 |
| 参照做法 | 参考开源实现中 `--user-data-dir`（专用 profile）+ `--remote-debugging-port` + 精确 `--remote-allow-origins` 的启动参数组合 | 该组合是已被验证的落地方式，见第 6 章借鉴来源 |

> **补充说明**：ADR-C05 的表述「附着用户真实已登录的浏览器」应准确理解为「附着**本方案专用的**、由人工完成登录的浏览器实例」，**不是**附着用户日常使用的浏览器。原文措辞易被误读为可以复用任意已登录浏览器，此处予以收口。

## 13. ADR 决策记录

### 13.1 决策明细

#### ADR-C01 采集端部署形态：集中单台
- 状态：提议
- 上下文：用户已确认集中一台 Win10/服务器；单站存量 133,965 条、长期千万级；账号来自各站长。
- 决策：单台集中部署，多站点通过「账号 ↔ 浏览器上下文」多路复用，队列串行执行。
- 后果：正面——运维一处收口、成本最低、与用户既有决策一致；负面——单机故障波及全部站点，且多账号同机存在关联风险（K6/K8）；资源上限需量化。
- 备选：每驿站一台（设备与运维成本 ×N，站长无 IT 能力）；混合（重点站点下沉）——均不选，成本与维护复杂度不匹配当前规模。

#### ADR-C02 采集账号归属：各驿站站长自有账号 + 集中托管登录态
- 状态：提议
- 上下文：只有站长账号在其自有机构权限内可见本站数据；系统无平台侧授权通道。
- 决策：使用站长自有账号；采集端**不代管凭据**，仅附着人工已登录的浏览器上下文。
- 后果：正面——权限天然收敛在自有驿站（红线 C1），无需平台授权；负面——登录态失效需站长人工重登（K2），账号健康度成为常态运维项。
- 备选：统一使用一个「超级账号」（存在越权风险，红线 C1 直接排除）；由系统代管站长密码自动登录（凭据托管，安全后果不可接受）——均不选。

#### ADR-C03 取数路线优先级：C 为主力、A 为首灌加速、B 并行评估
- 状态：提议
- 上下文：见第 6 章对比表。
- 决策：路线 C（页面上下文内响应监听）作为主力与首灌兜底；路线 A（原生导出）作为首灌加速通道，验证通过后启用；路线 B（开放平台 API）并行评估。
- 后果：正面——唯一已实测可行的组合，不触碰签名，合规可辩护；负面——依赖浏览器常驻与 DOM 触发器（K5），首灌时长受间隔下限主导。
- 备选：仅 A（未验证，可能字段不全 → 单点依赖）；仅 B（未验证可行性）——均不选。

#### ADR-C04 排除路线 D（自造请求 + 逆向 `anti-content`）
- 状态：已采纳（排除）
- 上下文：`anti-content` 为数百字符不透明风控签名，另有 `etag`/`pdd-id` 参与校验。
- 决策：**明确排除**自造请求与签名逆向。
- 后果：正面——避开合规事故与无上限维护成本；负面——放弃直连 HTTP 的轻量路径，必须承担浏览器常驻成本。
- 备选：mitmproxy 中间人解密（需装根证书，与红线 C3/C5 冲突）→ **仅登记为技术储备**；Crawlee proxy rotation / fingerprint 生成、undetected-chromedriver、puppeteer-stealth → **不引入**。

#### ADR-C05 登录态方案：CDP 附着本方案专用、由人工登录的浏览器实例
- 状态：提议（**含主智能体 Review 修订**）
- 上下文：凭据不能托管；浏览器自动头（Cookie/UA/Referer）不可自行复现。
- 决策：CDP 连接**本方案专用**的浏览器实例（借 BrowserForce 思路）；该实例由**人工完成登录**，采集端不自行托管登录态。
  - 澄清（Review 修订）：被排除的是**由程序代管凭据并自动登录**，**不是**「持久化 profile」本身——专用 profile（`--user-data-dir`）是必须的，否则每次都要人工重登。两者区别在「**谁完成登录**」：**人工登录 = 采纳；程序自动登录 = 排除**。
  - 该实例的信任边界与启动参数硬约束见 **10.2.1**（专用实例 / 仅登录目标站点 / 端口仅绑 127.0.0.1 / 禁止通配来源）。
- 后果：正面——零凭据落地、自动头天然正确、无需模拟指纹；负面——依赖人工保持登录（K2），且需标签页管理纪律（不与人工操作争抢页面）；**新增安全面**：CDP 通道本身是高权限入口，必须依赖 10.2.1 的硬约束收口（列入 K15）。
- 备选：程序代管站长密码并自动登录（凭据托管，安全后果不可接受）→ 不选；复用用户日常浏览器（会把该机全部站点登录态暴露给采集进程）→ 不选（改采专用实例）。
- ⚠️ **2026-09-19 实测补丁（必踩项）**：**`new_context()` 的隔离 ≠ 复用登录态** —— 新建 context **不继承**默认 context 的 Cookie。因此复用人工登录态必须走 **`browser.contexts[0]`**（即人工登录所在的那个 context），**不要**为了"隔离"而 new 一个 context，否则会拿到未登录页面。详见 18.3 补丁 3。

#### ADR-C06 采集端形态：常驻 daemon（托盘 + 远端可控），定时脚本仅作兜底
- 状态：提议
- 上下文：页面常驻复用是省成本前提（T4）；断点续传与配置下发需要长生命周期进程。
- 决策：Windows 服务 + 托盘常驻 daemon；定时脚本仅用于「补采/对账」类一次性任务。
- 后果：正面——页面实例复用、崩溃自愈、可远端控制；负面——进程守护与升级机制需自建（Windows 服务/看护）。
- 备选：纯定时脚本（每次冷启动浏览器 → 首屏 4.62MB JS 重复加载，成本与风控暴露面都高）→ 不选。
- ✅ **2026-09-19 实测确认**：**CDP 下 `browser.close()` 只断连、不杀 Chrome 进程** —— 这正是 daemon 常驻所需的语义：采集任务结束可释放 Playwright 连接，而浏览器与人工登录态**继续存活**，下次任务直接重连即可，无需重新登录。该行为是本条决策能成立的关键前提（否则每次任务结束都会丢掉登录态）。

#### ADR-C07 控制端与守护进程分离（借 agent-browser 结构）
- 状态：提议
- 上下文：需要「远端可控」但不能让服务端主动连入采集端。
- 决策：服务端只提供 HTTP 控制面（任务/配置/心跳），采集端出站轮询；本地仅暴露 127.0.0.1 控制端口。
- 后果：正面——无公网入站、攻击面小；负面——指令延迟受轮询周期约束。
- 备选：服务端直连采集端（需公网端口，安全后果差）→ 不选。

#### ADR-C08 采集端分层与模块边界
- 状态：提议
- 上下文：见 7.1/7.2。
- 决策：L1 控制层 / L2 守护进程层 / L3 浏览器连接层 / L4 采集队列层 / L5 限速熔断层 / L6 落库回推层 / L7 平台适配器层，依赖单向向下，L5 强制经过。
- 后果：正面——职责清晰、可单独测试、限速熔断无法被旁路；负面——层数多，初期实现量略大。
- 备选：单文件脚本（无法保障限速熔断强制性与断点能力）→ 不选；微服务拆分（过度设计）→ 不选。

#### ADR-C09 增量同步策略：首灌全量 + 日常增量（双模，兜底先行但有站点上限）
- 状态：提议（**含主智能体 Review 修订**）
- 上下文：V1 未验证前无法确定能否用时间窗口筛选。同时受两条硬前提约束：部署为集中单台（ADR-C01）、并发固定为 1（红线 C2）→ 单机日采集时长上限约 20 小时。
- 决策：首灌走全量；日常增量**先落地模式 2（全量轮扫兜底，已实测可行）**，V1 通过后切换模式 1（窗口增量）。两者共用幂等键与批次留痕。
  - **但模式 2 必须带站点数上限**：按 3~5 小时/站估算，单机最多支撑 **4~6 个站点**；超出后当日无法闭合。
  - 因此 V1 未通过期间必须择一：**(a)** 将启用站点数限制在 4~6 以内；**(b)** 模式 2 降级为**周度全量对账**，不承担日常增量职责。
  - **触发条件**：站点数 > 6 且 V1 仍未通过 → 模式 2 路径失效，须立即攻关 V1，不得靠加班/延长窗口硬扛（会直接产生 K1 缺口）。
  - ✅ **2026-09-19 更新：V1 已闭环，本条的过渡困境解除。** 实测确认请求体含 5 组日期区间参数（`inCabinetTime` 等，见第 17 章）→ **模式 1（窗口增量）可直接实现，无需先跑全量轮扫**。本条修订后的定位：**模式 1 为首选主路径；模式 2 降级为「周度全量对账 / 缺口回补」用途**，不再承担日常增量职责，站点数上限的约束随之解除。
- 后果：正面——今天即可落地，不赌未验证假设；负面——过渡能力**有明确天花板**，且天花板由站点数而非技术决定；站点数增长会先于 V1 结论到达，需提前排期。
- 备选：只做窗口增量（依赖 V1，未通过则完全无增量能力）→ 不选；提高并发以压缩时长（直接违反红线 C2）→ 不选。

#### ADR-C10 断点与游标持久化位置：采集端本地为主 + 服务端留痕
- 状态：提议
- 上下文：断点必须在采集端崩溃后仍可恢复；服务端需知任务进度。
- 决策：**权威游标存采集端本地 SQLite**（与请求上下文同生共死，避免双写不一致）；服务端只存任务状态与批次结果（可从本地重建）。
- 后果：正面——崩溃恢复不依赖网络、无双写竞态；负面——采集端磁盘损坏即丢游标（可用批次结果 + 全量轮扫重建）。
- 备选：游标存服务端（每页一次往返，放大请求量）→ 不选；Redis 存游标（TTL 过期即丢）→ 不选。

#### ADR-C11 千万级分区策略：按 `station_id` HASH 分区
- 状态：提议
- 上下文：MySQL 分区表要求唯一索引包含分区键；防重键为 `(station_id, waybill_no)`。
- 决策：在线主表按 `station_id` HASH 分区；主键采用 `(id, station_id)` 复合；归档表允许按时间 RANGE 分区。
- 后果：正面——防重键原样保留，防重能力不打折，单站查询命中单分区；负面——HASH 分区不便按时间收缩，需靠归档表清理；分区数调整需 `REORGANIZE`。
- 备选：时间 RANGE 分区（唯一键被迫补时间列 → 防重降级为「同分区内唯一」，跨期重复需业务层兜底）→ 不作为在线主方案；应用层分表（引入路由复杂度）→ 登记为备选，规模触发时启用。

#### ADR-C12 唯一键与幂等：保留 `(station_id, waybill_no)` + 批次留痕
- 状态：提议
- 上下文：db.md §1.3 一期采用「不依赖数据库唯一索引，Service 层查重」；但包裹表为批量写入且千万级，Service 层查重在批内成本高。
- 决策：包裹表**建立真实唯一索引** `(station_id, waybill_no)` 并用 upsert 幂等；批次号留痕到行级（`last_sync_batch_no`）与批次表。
- 后果：正面——幂等由数据库保证，批内竞态天然消除；负面——与一期「唯一性不靠数据库」的取舍口径不一致，需在二期文档显式说明差异理由（管理端低并发 vs 采集端批量写入）。若未来改用时间 RANGE 分区，该唯一键需补时间列、防重降级为分区内唯一 → 由「写入前查重 + 批次对账」兜底。
- 备选：仅 Service 层查重（千万级批量写入下不可行）→ 不选。

#### ADR-C13 冷热分离与历史归档
- 状态：提议
- 上下文：千万级 + 列表查询性能 + 禁止物理删除。
- 决策：热区（近 N 月，N 待定，建议 6 个月）+ `parcel_archive`（按时间 RANGE 分区）；按月下沉；归档前先做连续性校验。
- 后果：正面——在线表可控，历史可查；负面——查询需区分冷热（前端需提供「含历史」开关），归档任务本身需监控。
- 备选：不归档（千万级在线表索引膨胀、备份窗口过长）→ 不选。

#### ADR-C14 限速与熔断参数模型
- 状态：提议
- 上下文：红线 C2（并发 = 1、间隔下限、硬熔断）；实测单次 644ms；首灌 2680 页。
- 决策（**拟**，首期保守，观察后调整）：
  - 并发：**1**（硬约束，不可配置为 >1）；
  - 请求间隔下限：**暂定 ≥ 3s/请求**。⚠️ Review 修订：该值目前**无依据来源**——原稿称「不得低于站点 robots/条款声明的延迟要求，取两者较大值」，但该声明**尚未读取**（红线 C4 的「采集前读取」动作未执行）。故 3s 仅为**无依据的保守占位值**，须在 C4 完成 robots/条款快照后复核并回填依据（见 V8）；**复核前不得据 3s 做容量承诺**；
  - 抖动：在间隔下限之上叠加 ±30% 抖动（**仅平滑负载，非伪装**）；
  - 重试：单请求失败重试 ≤ 2 次，退避 5s / 15s；
  - 硬熔断：验证码 / 滑块、HTTP 403、HTTP 429、跳登录页、响应结构突变（`success` 缺失或 `result.resultList` 结构变化）→ 立即终止；
  - 恢复：**禁止自动恢复**，需人工确认（本地托盘确认 + 服务端任务状态置位）后从游标续采；
  - 熔断后同站点**强制降频**（间隔下限提升一档）再启动。
- 后果：正面——以时长换安全，风控暴露面最小；
  - 负面（**Review 修订，量化**）：本 ADR 的 ADR-C01（集中单台）+ C2（并发 1）已把**时间**变成唯一可调配资源，而间隔下限直接决定吞吐。按 3s 计：单站首灌模型值 **≈2.7h**（2680 × 3.644s ≈ 9766s），排期按 3~5h 留缓冲；折算日上限约 **4~6 站点/日**。
  - **敏感性提示**：若 robots/条款复核后间隔下限被迫提高（如 5s → 单站 ≈3.9h），站点上限随之下降；反之若能降到 2s，可支撑约 8~10 站。**该参数是本方案唯一的容量杠杆**，须在 V8 后重新评估并回写本章与 NFR。
- 备选：并发 = 2~3（直接违反红线 C2）；无间隔（触发风控概率高，风险不可控）→ 均不选。

#### ADR-C15 配置下发：采集端保持「薄」
- 状态：提议
- 上下文：接口路径、入参、翻页规则、字段映射都可能随平台变化；采集端在 Windows 上，升级成本高。
- 决策：以上全部由服务端 `/api/v1/crawler/*` 下发的配置接口提供（版本化 + 校验版本号），采集端热加载；采集端仅内置「触发与解析引擎」。
- 后果：正面——**已有平台的**参数变更不发版；负面——配置错误会导致全线静默失败 → 需配置校验 + 灰度（先单站点验证）。
  - **Review 修订（适用范围澄清）**：C15 的「不发版」**仅覆盖已有平台的参数变更**（接口路径、入参模板、分页规则、字段映射、限速参数）。**新增平台不在其覆盖范围内**——L7 适配器为代码，新增平台必须发版（见 C16 / K17）。原稿未作此区分，易被误读为「平台扩展零成本」。
- 备选：配置硬编码在采集端（每次变更都要重新分发到 Windows 主机）→ 不选。

#### ADR-C16 多平台适配器抽象
- 状态：提议
- 上下文：本期仅多多买菜门店端，但同类驿站平台众多（行业参照：驿微通适配 13 个驿站系统）。
- 决策：抽象 L7 适配器接口（入口路由 / 触发计划 / 响应匹配 / 分页元信息 / 字段映射），本期只实现一个；平台差异**全部**收口在适配器 + 服务端配置内。
- 后果：正面——新增平台不动核心层（队列/限速/落库零改动）；负面——存在抽象过早风险（用「一个实现 + 明确接口」控制风险，不预先实现第二个平台）；**且新增平台需采集端发版**（Review 修订，见 K17）——「不动核心层」≠「零成本」。同时**新平台的合规性与取数路线须重新评估**（每个平台的风控与条款不同，不得沿用本 ADR 的合规结论）。
- 备选：不做抽象（第二个平台时重构核心层）→ 不选；按平台拆多采集端 → 与 ADR-C01 冲突。

#### ADR-C17 同步任务模型
- 状态：提议
- 上下文：plan.md §3.2 要求任务状态机；db.md §6.2 预告 `sync_task` / `sync_log`。
- 决策（**拟**）：
  - `sync_task` 状态机：`PENDING → CLAIMED → RUNNING → (SUCCESS | FAILED | INTERRUPTED | BLOCKED)`；`INTERRUPTED`（熔断）、`BLOCKED`（登录态失效）为**必须人工介入**的终止态；
  - 领取：Redis `crawler:lock:{station_id}`（SETNX + TTL，继承 plan.md §3.3）；
  - 批次：每次任务产生 `batch_no`（拟：`{station_code}-{yyyyMMddHHmmss}-{seq}`），行级留痕到 `parcel.last_sync_batch_no`；
  - 重试：`FAILED` 可自动重试 1 次（间隔递增）；`INTERRUPTED` / `BLOCKED` **不自动重试**；
  - `sync_log` 记录页级结果摘要（页码 / 条数 / 耗时 / 结果码，**不含响应体明文**）。
- 后果：正面——状态可追溯、缺口可归因；负面——状态机引入额外的状态迁移测试成本。
- 备选：仅「成功/失败」两态（无法区分熔断与业务失败，缺口原因不可追）→ 不选。

#### ADR-C18 缺口检测与告警机制（制度级，非仅风险表）
- 状态：提议
- 上下文：K1「漏采即永久缺口」是本项目最高等级风险。
- 决策：落成四道**可执行**机制：
  1. **窗口连续性校验**（每次任务）：本次采集窗口的时间下界 ≤ 上次时间上界（允许重叠冗余），违反即判缺口 → 写 `sync_gap(station_id, gap_start, gap_end, status, batch_no)` → 告警；
  2. **窗口闭合率看板**（每日）：`闭合站点数 / 应采站点数`，目标 **100%**；非 100% 必须当日处理并留痕；
  3. **存量对账**（每周）：远端 `total` 与本地计数比对（口径一致性依赖 V3；口径未确认前，以「本轮扫取总条数 vs 本轮入库集合大小」做**同源对账**，不依赖平台留存语义）；
  4. **熔断即缺口**：熔断终止的任务一律标记「窗口未闭合」，进入缺口列表，**禁止跳过**；缺口只能通过补采转 `closed`，不允许「人工标记忽略」。
  - 告警出口：管理端看板红点 + 任务列表 + 采集端托盘提示；**若不满足**，二期需新增通知渠道（列为二期待建项，不假设既有）。
- 后果：正面——把「不可回补」的风险转化为可度量的运维指标；负面——需要日常运维投入（每日巡检）与看板开发量。
- 备选：仅写进风险表（无人执行，等价于无缓解）→ **明确不选**。

#### ADR-C19 运维与可观测
- 状态：提议
- 上下文：单机承载多站点，故障必须早发现。
- 决策（**拟**）：
  - 心跳：30s 一次，连续 3 次缺失判离线（K13）；
  - 日志：采集端本地滚动 30 天（脱敏），服务端 `sync_log` 仅存摘要；
  - 远程协助：参照行业做法（驿微通强制 ToDesk/向日葵）→ **本方案不强制安装第三方远控**，优先用 Windows 远程桌面/内网受控通道；如需第三方，须经安全评估 + 用户确认（不在架构层预设）；
  - 版本升级：服务端下发版本清单 → 采集端自检 → 人工确认后升级（生产只拉 Git 代码，产物走发布流程）；
  - 版本漂移锁定：浏览器禁用自动更新；记录页面版本横幅（实测形如 `v20260913.16.22.43#20250325#info`），变化即告警（K7）。
- 后果：正面——问题早发现、升级可控；负面——远程协助策略需与用户单独确认。
- 备选：无监控裸跑（K1 风险不可接受）→ 不选。

#### ADR-C20 与一期接口契约：`/api/v1/crawler/*` + 双认证 + 错误码分段
- 状态：提议
- 上下文：plan.md §3.3/§3.4 已定基调。
- 决策：
  - 接口组 `/api/v1/crawler/*`（拟：任务领取/心跳/配置拉取/批次回推/缺口上报/熔断上报）；响应结构沿用 api.md §1.2 统一 `{code, message, data}`；
  - 认证：`X-Crawler-Key`（API Key，独立于管理端 JWT 过滤器，白名单物理隔离）；
  - 错误码分段（**拟定义，待 api.md 二期版本落地**）：`6001` 任务不存在或状态非法、`6002` API Key 无效、`6003` 批次号重复或已提交、`6004` 驿站未绑定采集账号、`6005` 回推数据校验失败、`6006` 采集节点未注册或心跳超时；`7001` 包裹数据不存在、`7002` 运单号格式非法、`7003` 归属驿站不匹配（越权）。
- 后果：正面——与管理端物理隔离，互不影响；负面——新增一套认证与错误码段，需同步更新 api.md（二期版本）。
- 备选：复用 JWT（采集端无法承载交互式登录，且与管理端会话耦合）→ 不选。

#### ADR-C21 数据可见范围：启用 STATION_ADMIN
- 状态：提议
- 上下文：requirement.md §3.1 一期预留 `role=STATION_ADMIN`；db.md §3.3 已建 `idx_employee_station_id`。
- 决策：二期正式启用 `STATION_ADMIN`；包裹数据可见范围 = `employee.station_id` 对应驿站；ADMIN 可见全部；STAFF 二期不可见包裹模块。
- 后果：正面——零表结构改动（复用一期）；负面——站长与采集账号是**两个体系**（站长用自有平台账号采数、用系统账号看数），需在文档与培训中讲清，避免混淆。
- 备选：为站长单独设「采集账号」权限实体（一期已预留角色，重复造）→ 不选。

### 17.3 重大修正：`retentionDays` 不是平台留存窗口

**实测证据（bundle 源码三处独立佐证）**：

1. 它是**筛选表单控件的绑定值**：`label:"滞留天数"`、`value: x.retentionDays`、`options: X.options`（下拉）。
2. 它是**表格列**：`{ dataIndex:"retentionDays", title:"滞留天数" }`。
3. 它是**详情弹窗的展示字段**：`v.retentionDays`，与「包裹属性」并列。

**结论**：`retentionDays` = **包裹在站内的滞留天数**（业务属性），**与平台数据留存策略毫无关系**。

**必须撤回的原结论**：

| 原表述（v1.0/v1.1） | 修正 |
| ---- | ---- |
| 「`retentionDays` 疑似平台留存窗口，推断 ≈4~5 个月」 | **推断作废**（推理依据本身就是误读字段名） |
| 「漏采即永久缺口」列为**高**级风险 | 降为**中**级；风险仍未消除（平台是否长期保留全量历史**未知**），但原量化依据不成立 |
| V3「`retentionDays` 是否等于留存窗口」 | 问题重定义为「**平台是否存在数据留存上限**」，验证方式改为按极早时间区间筛选探测 |

> **教训（写入项目记忆）**：本 ADR 曾据一个**字段名**（`retentionDays`）推出「平台留存 4~5 个月」并升级为最高等级风险，随后围绕它设计了整套缺口制度。**字段名不等于语义**——凡涉及外部系统语义的判断，必须以实测（bundle / 真实请求 / 官方文档）为准，不得望文生义。

## 18. Python 可行性实测验证与 CDP 落地补丁（2026-09-19 · 实机验证）

> 本章记录**实机验证**结论（非纸面推断），来源：本机独立 profile Chrome + **Python 3.12 + Playwright 1.63**，实跑 3 组 POC。
> **本章三条补丁为强制落地项** —— 未打补丁直接上线必踩，且踩的是"看起来能跑、实际拿不到数据"的隐性坑。

### 18.1 验证环境

| 项 | 值 |
| ---- | ---- |
| 运行时 | Python 3.12 |
| 浏览器自动化 | Playwright 1.63 |
| 浏览器 | 独立 profile 的 Chrome（与 daemon 设计一致） |
| 连接方式 | `connect_over_cdp()` |
| 验证方式 | 3 组 POC 实跑 |

| 能力 | Python 落地方式 | 实测结论 |
| ---- | ---- | ---- |

### 18.3 三个必须落地的补丁（强制）

#### 补丁 1 — 下载事件不是白拿的（CDP 连上后必须显式开启）

**现象**：CDP 连上的浏览器由 **Chrome 自身处理下载**，Playwright 的 `page.on("download")` **不触发**。

**补丁**：显式开启下载行为（`Browser.setDownloadBehavior`）：

```python
cdp = ctx.new_cdp_session(page)
cdp.send("Browser.setDownloadBehavior", {
    "behavior": "allow",
    "eventsEnabled": True,
    "downloadPath": r"<采集端受控下载目录>",
})
```

补上后 `expect_download()` + `save_as()` 恢复正常，可拿到导出文件（实测 `report.csv`）。

> **影响面**：路线 A（导出通道）**全部依赖此补丁**；不打补丁会表现为"点了导出但永远等不到文件"。对应 8.3。

#### 补丁 2 — `page.goto()` 命中附件 URL 会抛异常，但文件其实已落盘

**现象**：`page.goto()` 直接打开附件 URL → 抛 `Error: Page.goto: Download is starting`；**但实测文件已落盘**。

**补丁（两层）**：

1. **必须 try/except** 包裹：该异常**不代表失败**，不得据此判定取件失败；
2. **更稳的兜底**：监听 **CDP 层 `Browser.downloadWillBegin`**（实测 1 条事件稳定命中，**不依赖 Playwright 事件**）。

> **影响面**：若按"异常即失败"处理，会导致**导出件已下载却被判失败 → 重复触发导出 → 撞频次限制**（V2 未验证的项）。对应 8.3 与 ADR-C17 的失败判定逻辑。

#### 补丁 3 — `new_context()` 隔离 ≠ 复用登录态（**最易踩**）

**现象**：实测**新建 context 不继承**默认 context 的 Cookie。

**补丁**：复用人工登录态必须走 **`browser.contexts[0]`**（人工登录所在的那个 context）。

> **影响面**：这与 ADR-C05「CDP 附着已登录浏览器」直接相关。若为了"会话隔离"而 `new_context()`，会拿到**未登录页面**，表现为"连上了但被跳登录页"。**隔离与登录态复用是两件事，不能混用同一个手段。**
> 多驿站多账号场景下，正确做法是**每个账号一个独立的浏览器实例/profile**（各自的 `contexts[0]`），而**不是**在同一实例里 new 多个 context。

### 18.4 其它实测确认（两点）

| 项 | 实测结论 | 落地要求 |
| ---- | ---- | ---- |
| CDP 端口监听地址 | `--remote-debugging-port` **默认只 LISTEN 在 `127.0.0.1`** | ✅ 无需额外加固；**但绝不能加 `--remote-debugging-address=0.0.0.0`** → 写入**装机 checklist** 逐项核对（已是 10.2.1 条款） |

## 19. 多源（多通道）采集策略

> **本章性质**：**追加章节**，不改动 §1–§18 任何内容与编号。本章回答「同一份数据用哪条取数通道、什么时候用哪条、坏了怎么退」。
> **触发输入（用户口径，2026-09-19）**：长期频繁调用平台导出会积累风控风险 → **导出通道必须限频，不得作为高频轮询手段**。
> **沿用既有风控策略**：**限速 + 熔断，不做伪装**。本章**不引入** UA 轮换、代理/IP 轮换、CAPTCHA 打码、指纹伪造、反检测伪装；不引入 stealth / undetected / fingerprint / proxy / camoufox / nodriver 类库（与规划 §12.1 依赖黑名单一致）；mitmproxy 仍仅作技术储备、不进实现路径（ADR §6.3）。红线 **C1–C5 全部有效**。

### 19.1 术语校正与范围

| 项 | 结论 |
| ---- | ---- |
| 本文「多源」指什么 | **多取数通道**（same account、same page、same permissions，只是把数据取下来的机制不同）。**不是**多伪装手段、多账号、多 IP、多 UA |
| 与 §6 路线的关系 | 路线 **C（页面上下文内响应监听）** 被细化为 **通道 C1 / C2 / C3** 三种实现机制；路线 **A（平台原生导出）** = 通道 **A**；路线 **B（开放平台 API）** = 通道 **B**；路线 **D（自造请求 + 逆向 `anti-content`）** = **仍为明确排除**（ADR-C04），本章不再讨论 |
| 不变的部分 | 采集账号归属（ADR-C02）、登录态方案（ADR-C05 / 18.3 补丁 3）、限速熔断（ADR-C14）、分层（ADR-C08）**全部不变**；本章只细化「取数机制」这一维度 |
| 通道命名空间 | ⚠️ **命名冲突提醒**：通道号 `C1/C2/C3` 与合规红线号 `C1–C5`（§3.3）字形相同、语义无关。**本章及后续文档一律写作「通道 C1 / 通道 C2 / 通道 C3」**，纯数字编号仅用于红线。该约定需在二期全部文档与代码注释中沿用 |

> **范围外（明确不做）**：不做多通道**并行同采同一份数据**（见 19.3）；不做通道级伪装差异化；不做「导出通道自动扩容」；不新增 ADR-Cxx 决策编号（本章为既有 ADR-C03 的细化，不另立决策）。

### 19.2 通道清单与能力矩阵

> **暴露面等级**定义（本章统一口径）：**单次触发在平台侧留下的可观测痕迹强度**。「低」= 与普通人工操作无差别且无额外留痕；「中」= 与人工操作同形、但频次由采集决定；「高」= 平台侧生成显式记录（任务、操作人、资源消耗），可被审计与回溯。

| 通道 | 机制 | 取数触发方式 | 数据完整度 | 暴露面等级 | 断点友好度 | 适用场景 | 依赖的待验证项 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| **通道 C1** | **页面驱动 + Playwright 原生响应监听**（`page.on("response")` / `page.expect_response(predicate)`） | 由**页面自身**发起请求（点击查询 / 翻页）；采集端仅旁路读响应 | **中高**：拿到 `query_waybill` 响应 JSON 全字段（实测字段见 §5.1 / §17.2）；**拿不到请求体**（`postData` 可能为空） | **中** | **高**（`pageNo` 游标，天然可断点续传，ADR-C10） | **日常增量主力** + 首灌分页全量兜底 | V6（浏览器自动头是否存在）、V8（间隔下限取值） |
| **通道 C2** | **CDP `Network` 域直采**（`Network.enable` / `responseReceived` / `loadingFinished` / `getResponseBody` / `getRequestPostData`） | 同 C1（仍由页面动作触发）；采集端在 CDP 层取 body 与请求体 | **最高（含取证级）**：响应体原文 + **请求体**（`getRequestPostData`），可复现「请求 → 响应」完整对照 | **中**（**不新增网络请求**；`Network.enable` 属客户端本地行为，不提高服务端可见暴露面） | **中**（与 C1 共用游标；本身不持有分页语义） | ① C1 取不到 body 时的**降级承接**；② **取证**（字段口径核对、结构突变定位）；③ 请求体确认（如筛选入参映射复核） | 本策略新增 **V14 / V15**（长跑资源、取 body 失败率） |
| **通道 C3** | **HAR 录制 + 离线解析**（`browser.new_context(record_har_path=...)` / `context.tracing.start_har()`，后者 Added in v1.60） | 同 C1（页面动作触发），**录制全量网络流**，**离线**解析 | **最高（含噪声）**：覆盖全部请求/响应（含非 XHR 资源），可离线反复分析 | **中**（不新增请求；但页面长时停留） | **低**（一次性批量抓包，不承担断点续传职责） | ① **结构测绘**（摸清页面全部接口与调用时序）；② 一次性批量抓包（小窗口）；③ 与 §19.8.2「离线解析」流水线配套 | 本策略新增 **V13**（HAR 对性能/内存/体积的影响） |
| **通道 A** | **平台原生导出**（运单查询页「导出Excel」→ 下载任务页取件 → 解析文件） | **显式写式触发**（创建导出任务）→ 轮询任务状态 → 取件 | **未验证**：取决于导出字段集（`operationList` 等是否包含，V2 未闭环） | **高**：平台侧生成任务记录、可审计操作人、消耗平台计算/存储资源 | **中**（导出件实测约 1 天失效，须在有效期内取件，§5.4） | **仅**：① 首灌**一次性加速**；② **周度对账**（ADR-C18 第 3 条存量对账）。**不承担日常增量** | **V2**（导出四项）、本策略新增 **V12**（限频阈值） |
| **通道 B** | **开放平台 API**（`open.pinduoduo.com` + 驿站账号授权） | 授权后按接口契约直连（**平台官方通道**） | 未验证：取决于授权范围与 API 字段集 | **最低**（官方授权通道） | **高**（接口语义自带分页/时间窗） | **长期目标**：若可用则应迁移至此（最合规、最稳定） | **V5**（是否存在运单/物流类 API 且可授权） |

> **共同约束**：五条通道**共用同一套** L5 限速熔断层（并发 = 1、间隔下限、5 类硬熔断，ADR-C14）与同一套幂等键 `(station_id, waybill_no)`（ADR-C12）。**通道不得自带独立的限速旁路**。

### 19.3 通道职责分工（关键：不是平级多选）

| 通道 | 定位 | 说明 |
| ---- | ---- | ---- |
| 通道 C1 | **增量主力** | 日常增量（ADR-C09 模式 1 窗口增量）在 C1 上跑，理由：请求形态与人工操作完全同形、游标天然可断点、不触碰签名 |
| 通道 C2 | **响应体完整性与取证** | 只在两种情形出场：① C1 未取到 body 时**降级承接**；② **取证**（核对请求/响应口径、定位结构突变）。**不作为常规增量通道**（同一份数据只需一次请求，多通道同采无收益） |
| 通道 C3 | **结构测绘与一次性批量抓包** | 用途是「把页面的接口地图画出来」与「小窗口一次性抓包离线分析」，属于**工程分析与验证手段**，不是生产取数路径 |
| 通道 A | **仅首灌一次性加速 + 周度对账** | **不得**用于日常增量、不得用于补少量数据；受 19.6 限频规格硬约束 |
| 通道 B | **长期目标** | 在 V5 结论出来前不占用排期、不阻塞二期 |

**为什么不做「多通道并行同采同一数据」（强制纪律）**：

1. **风控暴露面 = 请求次数 × 通道显式度**。同采同一份数据会把请求数翻倍，同时叠加两种通道的暴露特征，与用户 2026-09-19 提出的担忧**直接相悖**；
2. **幂等键会掩盖问题**：`(station_id, waybill_no)` upsert 会让重复数据"看起来正常入库"，反而掩盖通道异常；
3. **同一时刻只允许一个采集动作**（与红线 C2「并发 = 1」广义解读一致）：导出任务运行期间**不得**同时跑分页采集。

> ⚠️ **唯一例外**：**PoC 阶段**允许对同一页面**双注册**（C1 事件 + C2 CDP，仅观测统计）以量化 C1/C2 差异与 `getResponseBody` 失败率，**验证结束即移除，生产不启用**（见 V15）。

### 19.4 通道选择器（ChannelSelector）与调度

| 项 | 内容 |
| ---- | ---- |
| **归属层** | **L4 采集队列层**（新增 `ChannelSelector` 子模块）。**不是 L2**。 |
| 归属理由 | ① 「任务 → 执行路径」的决策属队列调度范畴；② 降级链必须与**游标 / 批次状态**（L4 本地 SQLite 权威，ADR-C10）联动，放 L2 会造成 L2 跨层回读 L4，违反 ADR-C08 依赖方向；③ L2 的定位是「保持薄的进程/心跳/装配层」（§7.2），不应携带决策逻辑 |
| 分层合规 | 选择器只依赖**接口** `ChannelDriver`（`capabilities()` / `run(task, cursor)`），实现归 **L7 适配器层**（含平台差异），运行期由 L2 装配注入（与 §7.1「L7 被 L2/L4/L6 以接口方式使用」一致）。**L4–L6 不得 import L7 实现**，仍由规划 §12.1 的 `import-linter` 契约强制 |
| **输入** | ① **任务类型**：首灌 / 增量 / 对账 / 取证 / 结构测绘；② **站点通道策略**（L1 下发、经 L2 注入：允许通道集合、优先级覆盖、通道限频参数）；③ **通道健康度**（近期成功率、降级次数、熔断次数；来源为 L4 本地批次留痕 + L1 下发的健康度摘要）；④ **前置条件**（导出额度是否可用、开放平台授权是否存在、V2 是否闭环） |
| **输出** | ① **选定主通道**；② **降级顺序**（有序列表）；③ **决策理由码**（写入 `sync_batch.source_channel` 与决策日志，便于缺口归因） |
| 输出示例（无真实数据） | `task=incremental, station=<占位>, primary=C1, fallback=[C2], reason=CH_DEFAULT_INCREMENTAL` |

**任务类型 → 通道决策表（拟）**：

| 任务类型 | 主通道 | 降级顺序 | 备注 |
| ---- | ---- | ---- | ---- |
| 首灌 | 通道 A（**仅当** V2 闭环且当日额度可用） | A → C1 → C2 | V2 未闭环则**直接 C1**（§6.3 第 3 条：A 不得作为唯一首灌手段） |
| 增量 | 通道 C1 | C1 → C2 → **熔断终止** | **不降级到 A**（A 非增量通道） |
| 对账 | 通道 A（周度） | A → C3（一次性抓包） → C1（同源对账兜底） | 口径见 19.7 |
| 取证 | 通道 C2 | 无（取证失败即出报告） | C2 是唯一同时拿到请求体与响应体的通道 |
| 结构测绘 | 通道 C3 | 无（属一次性分析任务） | 产物入受控目录并脱敏（19.8） |

> **配置驱动**：上表按 ADR-C15 由 L1 **下发配置**承载（不属于代码），**通道实现本身是代码、需发版**（见 19.10）。

### 19.5 降级链与恢复

| 级 | 降级路径 | 触发条件 | 最大尝试次数 | 熔断边界 |
| ---- | ---- | ---- | ---- | ---- |
| 1 | **C1 → C2** | C1 连续 **3 页**未收到可匹配响应，**且** CDP 侧观测到页面请求确实发生（说明是"事件/body 取不到"，不是"触发器坏"） | 每任务 **1 次**降级，不允许来回反复切换 | 不熔断，仅记录 `degrade_reason` |
| 2 | **A → C1** | 导出任务创建失败 / 任务失效 / 解析后字段完整度不达标（V2 口径） | 每站**当日不再新建**导出任务（额度计入，见 19.6） | 不熔断；登记 `sync_log` 后回退 |
| 3 | **C2 → 熔断终止** | ① 硬熔断 5 类命中（验证码/滑块、403、429、跳登录、响应结构突变，ADR-C14）；② `getResponseBody` 失败占比超阈值（阈值见 V15） | **0**（不重试） | 站点级熔断，任务置 `interrupted` + 缺口登记 |
| 4 | **通道不可用标记** | 同通道同站点**连续 2 次**降级或失败 | 该通道对该站点置 `unhealthy`，**当日不再选用** | 需**人工复核后解除**，**禁止自动恢复**（沿用 ADR-C14/C17） |
| 5 | **跨站点通道级告警** | 同一通道在 **≥2 个站点**同时降级/失败 | 触发通道级告警（疑似平台整体变更，对应 K4） | 不自动全局停采，由人工判定 |

**恢复规则（沿用既有约定）**：

1. **熔断后禁止自动恢复**：需人工确认（本地托盘确认 + 服务端状态置位）后**从游标处续采**，续采走原主通道；
2. **降级是可逆的**：通道 `unhealthy` 解除后，下次任务按决策表重新选主通道（不"记住降级"作为默认）；
3. **降级不改数据语义**：无论走哪条通道，落库前一律经同一 `normalize`（19.7），**下游代码不得感知通道差异**。

### 19.6 导出通道限频规格（回应「长期频繁导出积累风控风险」）

| 参数 | 建议值 | 说明 |
| ---- | ---- | ---- |
| **每站每日导出任务创建上限** | **≤ 1 次/日**（周度对账场景：**≤ 3 次/周**，与日上限**取小**） | **未实测**，属保守占位值 → **V12** |
| **全局并发** | **= 1** | 导出任务与分页采集**互斥**：同一时刻仅一个采集动作在跑（不得叠加暴露面） |
| **任务复用** | 创建前先查「下载任务」列表，命中**同名 + 生成中/已完成**的任务则**复用，不新建** | 复用可避免因误判重复触发（对应 §18.3 补丁 2 的误判风险） |
| **失效处理** | 任务失效 → **当日不再新建**（额度已计入），转 C1；原因与时间写 `sync_log` | 不因失效而"补一次" |
| **取件窗口** | 任务完成后**尽快取件**（实测样本约 1 天失效，§5.4） | 取件失败**不重建任务** |
| **禁用场景** | ❌ 不得用于日常增量；❌ 不得用于补少量/补单条；❌ 不得作为"接口取不到时的替代轮询" | 违者按红线 C2 处理 |
| 参数归属 | 由 L1 配置下发（ADR-C15），随站点粒度可收紧、**不得放宽至上限以上** | 采集端**不得**本地提高该上限 |

**为什么导出不宜作为高频轮询手段（三条理由）**：

1. **留痕显式度远高于分页查询**：导出会在「下载任务」列表生成记录、可审计操作人、占用平台生成与存储资源；分页查询与人工操作完全同形。同样的调用次数，导出的风控可见度**更高**；
2. **生命周期与资源成本由平台承担**：任务从「生成中 → 已完成 → 已失效」的完整链路，本质是让平台为采集做批处理，高频调用是典型的异常使用特征；
3. **失败代价不对称**：导出失败（或误判失败）会诱发**重复触发**，直接放大调用次数（§18.3 补丁 2 已实测过该风险路径）。

> ⚠️ **限频参数未实测**：上述「≤1 次/日」**无平台侧依据**，属保守占位。**不得据该值做"导出可承担周度全量对账"的容量承诺**，须先完成 **V12**。参数本身**不是安全边界**——它降低暴露面，但**不能保证**不触发平台风控。

### 19.7 统一归一化与跨通道对账

**统一信封（所有通道产出必须包成同一结构，再进 L6）**：

```json
{
  "source_channel": "C1 | C2 | C3 | A | B",
  "station_id": "<占位>",
  "batch_no": "<station>-<yyyyMMddHHmmss>-<seq>",
  "captured_at": "<ISO8601>",
  "raw": { }
}
```

| 项 | 约定 |
| ---- | ---- |
| 归一化位置 | **L6 落库回推层** 的 `normalize(envelope)`（ADR-C08 单一入口）；**L7 适配器只负责把原始载荷包成信封**，不做字段业务语义判断之外的加工 |
| 通道无关性 | 下游（脱敏、校验、分批回推、幂等 upsert）**只认信封，不认通道**；新增通道**不改 L6 以下任何代码**（19.10） |
| 对账口径 1：同源对账（每任务） | 本轮扫取条数 vs 本轮入库集合（去重后）→ 差异 ≠ 0 即查（既有 ADR-C18 第 3 条，不依赖平台留存语义） |
| 对账口径 2：跨通道对账（周度） | 通道 A 导出件的 `waybill_no` 集合 vs 同期通道 C1 分页集合 → 统计**缺失率 / 字段差异率**；差异率阈值拟 **≤0.5%**（**未实测，随 V12 一并标定**），超阈值即告警 |
| 冲突裁决 1（字段值冲突） | 优先取 `gmtModified` **更晚**者；`gmtModified` 相同则取 `captured_at` 更晚者 |
| 冲突裁决 2（空值保护） | **空值不覆盖非空**：导出件缺列/空列**不得**抹掉分页已取到的字段值 |
| 冲突裁决 3（数组字段） | `operationList` 等数组字段取**并集去重**（**拟**；前提是导出件确实含该字段 → 依赖 V2 结论，未闭环前按裁决 1 处理） |
| 冲突裁决 4（集合差异） | 跨通道集合差异**只告警，不自动删除行**（沿用 ADR-C13「禁止物理删除」） |
| 仲裁依据 | 对齐规划 §14.3：**实测事实优先** > 决策层 > 规划层 > 其他；本节的裁决规则本身属"决策层"，若与实测冲突，以实测为准并回填本节 |

### 19.8 抓包层技术规格（可直接实现）

#### 19.8.1 原生监听（C1）与 CDP 直采（C2）的取舍与组合

| 维度 | 用 C1（Playwright 原生） | 用 C2（CDP 直采） |
| ---- | ---- | ---- |
| 选择原则 | **默认**：能拿到响应体就用 C1（API 稳定、类型友好、无需管理 session） | **补位**：需要**请求体**、或 C1 拿不到 body、或需要核对"请求→响应"完整对照时 |
| 组合方式 | **同一任务同一时刻只启用一条采数路径**（19.3 纪律）；C2 作为 C1 的**承接者**，不做并行同采（PoC 统计除外，见 V15） |
| 生命周期 | 随 `page` 对象；页面复用即天然复用 | CDP session **显式创建/关闭**，长跑需评估是否周期性重建（V14） |
| 依赖的强制补丁 | 复用登录态必须走 `browser.contexts[0]`（**§18.3 补丁 3**） | 同左。⚠️ 若为"隔离"而 `new_context()`，C2 也只会拿到**未登录页面**的流量 |

**C1 关键写法（示意，非最终代码）**：

```python
def on_response(resp):
    # 平台无关：是否命中目标接口由 L7 适配器判定，核心层不出现平台字段名（规划 §12.1 黑名单）
    if not adapter.match_response(resp.url):
        return
    sink.submit(resp.json())          # 只取所需字段，避免整页响应体常驻内存

page.on("response", on_response)      # 旁路读取：不改写、不阻断业务响应

with page.expect_response(adapter.match_response, timeout=<拟>):
    trigger_next_page()               # 请求仍由页面自身发起（翻页/查询），采集端不构造请求
```

**C2 关键命令 / 事件序列（示意，非最终代码）**：

```python
cdp = ctx.new_cdp_session(page)       # ctx 必须是人工登录所在实例的 contexts[0]（补丁 3）
cdp.send("Network.enable")

# 事件回调入参形态以 Playwright CDP 官方 API 文档为准（存疑，见本节末「不确定项」）
cdp.on("Network.responseReceived", on_response_received)
cdp.on("Network.loadingFinished", on_loading_finished)
cdp.on("Network.requestWillBeSent", on_request_will_be_sent)
```

```python
def on_response_received(params):
    url = params["response"]["url"]
    if adapter.match_response(url):
        pending[params["requestId"]] = params["response"]   # 仅登记，不在此取 body

def on_loading_finished(params):
    rid = params["requestId"]
    if rid not in pending:
        return
    # 【坑 2：时序】必须在 loadingFinished 到达后「尽快」取 body，不要等整页 idle
    try:
        body = cdp.send("Network.getResponseBody", {"requestId": rid})
    except Exception:
        # 【坑 1：缓存命中 / 被重定向 / 已过期 的资源】抛 No resource with given identifier
        # 应对：丢弃本次，改为「重新触发页面动作」（不是重放 HTTP 请求 —— 请求仍由页面自身发起）
        mark_need_retrigger(rid)
        pending.pop(rid, None)
        return
    # 【坑 3：编码】base64Encoded 为真时必须解码
    raw = base64.b64decode(body["body"]) if body["base64Encoded"] else body["body"]
    # 请求体：优先 getRequestPostData（requestWillBeSent 的 postData 可能为空）
    post = cdp.send("Network.getRequestPostData", {"requestId": rid})
    sink.submit(build_envelope("C2", raw, post))
    pending.pop(rid, None)
```

**三个已知坑（强制写入实现与代码评审清单）**：

| # | 坑 | 现象 | 应对（强制） |
| ---- | ---- | ---- | ---- |
| 1 | `getResponseBody` 取不到 | 对**缓存命中的、被重定向的、已过期的**资源抛 `No resource with given identifier` | ① try/except 包裹，**不得**据此判定任务失败；② 改为**重新触发页面动作**（保持"请求由页面发起"的合规边界）；③ 失败率纳入 V15 统计 |
| 2 | 时序 | body 可能被后续导航/清理后失效 | 在匹配事件后**尽快**取（`loadingFinished` 回调内即取），**不得**延迟到整页 idle 或批量后处理 |
| 3 | 编码 | `base64Encoded` 为真时 body 是 base64 | 必须解码；二进制/编码判定需一并处理（HAR 侧对应 `content.encoding`） |

> **`page.route()` 的定位**：本方案**不需要**它取数（C1/C2 都是只读旁路）。若使用，**仅限本地只读观察**，**严禁** `route.fulfill()` 改写业务响应（会把"旁路采集"变成"篡改流量"，触碰红线 C3 与项目规则安全基线）。

#### 19.8.2 HAR 录制与离线解析（C3）

| 项 | 结论 |
| ---- | ---- |
| 两种入口 | ① `browser.new_context(record_har_path=...)`（上下文级）；② `context.tracing.start_har()`（Tracing 级，Added in v1.60）。本机 Playwright 1.63（§18.1）**理论上均可** |
| **与补丁 3 的关系（关键）** | HAR 必须在**人工登录所在的上下文**上录制（即 `browser.contexts[0]`）。若为"干净录制"而 `new_context()`，录到的是**未登录上下文**的流量 —— 与 §18.3 补丁 3 同一根因，**必踩** |
| 与补丁 1 / 2 的关系 | **无依赖**：HAR 不承担导出件下载（导出取件走通道 A + 补丁 1/2）。HAR 仅用于**结构测绘**与一次性分析 |
| 离线解析 | 借鉴 apisniff 的「先抓 → 后离线解析 → 再检测漂移」结构：录制归录制、解析归离线（解析器不得依赖实时会话）；可产出接口清单与「响应结构快照」用于 K4 漂移比对 |
| 噪声控制 | 借鉴 webtap-tool 的噪声过滤思路：录制时按 URL 前缀/资源类型过滤（埋点、静态资源、`apm.*` 报错等），避免 HAR 体积失控（§5.5 已排除 `apm.pinduoduo.com` 噪声） |
| 性能 | 长时录制对页面性能与内存的影响**未实测** → **V13** |

#### 19.8.3 抓包产物落盘组织与脱敏要求

**目录组织（借鉴 browser-harness gist 的「请求体 / 响应体 / meta 三元组」）**：

```text
capture/{station_code}/{batch_no}/
  ├─ 0001.req.json     # 请求体（落盘前脱敏）
  ├─ 0001.resp.json    # 响应体（默认不落原文，见下表）
  ├─ 0001.meta.json    # url / method / status / 时间 / 耗时 / requestId / source_channel
  ├─ session.har       # C3 结构测绘产物（仅在受控目录，任务结束即脱敏后销毁）
  └─ README.txt        # 数据分级说明 + 「禁止入 Git / 禁止上传」告警
```

| 要求 | 内容 |
| ---- | ---- |
| **默认不落响应体原文** | 响应体含收件人/手机号/运单号，属**真实业务数据**（红线 C5）。**默认**只落「通道无关的关键字段 + meta」；**仅取证任务**落响应体原文，且**落盘前脱敏**（对齐 ADR 9.4） |
| HAR 的敏感面 | HAR 内含 `Cookie` / `Set-Cookie` / `Authorization` / 平台风控头（`anti-content` / `etag` / `pdd-id`）→ **必须脱敏**：录制后按 JSON 遍历把上述字段置为空占位；**不得**明文长期留存 |
| ⚠️ **必须写入文档的告警（引用 apisniff 官方说明）** | **抓包产物包含 cookie / token 等敏感数据，不得提交、不得上传**。本方案据此规定：`capture/` 与 `*.har` **一律不入 Git**（对齐规划 §14.5 禁止项），只在采集端受控目录，且取证/测绘任务结束后按保留期销毁 |
| 保留期 | 取证产物保留期**拟 ≤ 7 天**（**未实测**，随 V13 一并标定）；HAR 结构测绘产物用后即删（结论留档，原文不留） |
| 幂等 | 落盘仅服务于 PoC 与取证；**入库路径仍走** `(station_id, waybill_no)` upsert（ADR-C12），落盘文件**不反向覆盖**库内数据 |
| 不确定项 | HAR 对**二进制下载类响应**的表示方式、以及 `start_har` 的具体参数与停止方式 —— **不确定，需查 Playwright 官方 Tracing/Network 文档**（并入 V13） |

## 20. 凭据托管与自动登录（V10 决议）

> **本章性质**：**追加章节**，不改动 §1–§19 任何内容与编号（沿用 §19 的做法）。本章落地用户 2026-09-19 决议「放开凭据代管」，逐条对照修订受影响的红线与既有决策，并给出凭据托管与自动登录的设计。
> **本章新增决策**：`ADR-C22 凭据托管`（20.3）、`ADR-C23 自动登录与失败回落`（20.4）；**待下轮回填** §13.1/§13.2（回填义务见 20.7.1）。
> **不在本章范围**：不改变路线 C/A/B/D 结论、不改变 L1–L7 分层与依赖方向、不改变「真微服务」重评审相关事项（另派）。

### 20.1 背景与决议

**V10 的空洞根因（是取舍矛盾，不是信息缺失）**

原 ADR 把 V10 记为「设计空洞」（§12）与「工程组织问题」（§18.7）。进一步分析后，其本质是**架构取舍的互斥**：

| 命题 A | 命题 B | 结论 |
| ---- | ---- | ---- |
| 程序持有站长账号密码并自动登录（可无人值守） | 不代管凭据（原 ADR-C02/C05、§10.2） | **不可兼得** |

此前方案选了 B，因而必然留下「集中机无人值守时谁来登录」的空洞；同类商业产品选了 A，故可实现无人值守。

**行业形态旁证（仅作形态参照）**：驿微通（`ywt8.com`，查件机器人，商业产品）官方表述的运行环境为「一台 Win10/11 专业版机器常驻 + 配置各快递系统账号密码并全部登录成功」，已对接 13 个快递/驿站系统（含「多多驿站」「多多乡镇」）。来源：`ywt8.com` 官网。**仅引为「行业存在该可行形态」的旁证，不引用其代码或任何未公开实现。**

**用户决议（2026-09-19，原文口径）**：V10 选择「**放开凭据代管（需改红线）**」——允许采集端加密保存站长账号凭据并自动登录，以实现无人值守；用户已知悉并接受该选择需要修订既有红线。

**本次决议的生效范围**

| 明确生效 | 明确不生效 |
| ---- | ---- |
| 允许采集端**加密托管站长自有平台账号凭据**，用于**自动登录/续登**（仅本方案专用采集端、仅目标站点、仅只读采集） | 不改变「账号来自各站长自有账号」（红线 C1 不变） |
| 允许在熔断前执行**受次数上限约束**的会话自愈（20.4） | 不放开任何反检测/绕过手段（红线 C3 不变，见 20.2/20.9） |
| 凭据仅存**采集端本地**（DPAPI 密文） | 服务端仍**零平台凭据**（§10.2 定位不变） |

### 20.2 红线修订（必须逐条对照原文改写）

> 本小节逐条给出**原条款原文 → 修订后条款**，并说明删了什么、加了什么、为什么。生效的硬前置见 20.2.9。

#### 20.2.1 红线 C2（限速 + 熔断）—— 修订

**原条款原文**（§3.3）：
- 红线：「**限速 + 熔断**：串行请求、请求间隔下限、并发 = 1；命中验证码 / 403 / 429 / 跳登录 / 结构突变即**立即终止并出报告**」
- 落地要求：「限速熔断层为强制经过路径，熔断后**禁止自动重试绕过**」

**修订后条款**：
- 红线：串行请求、请求间隔下限、并发 = 1 **不变**；命中验证码 / 403 / 429 / 结构突变仍**立即终止并出报告**；**新增**：「跳登录」触发后，允许在熔断**之前**执行一次**受次数上限约束的会话自愈**（20.4），自愈仍失败即按原样熔断并出报告。
- 落地要求：追加「会话自愈**不属于**『自动重试绕过』；其上限为每站每任务 ≤ 1 次（拟，未实测），超限即终止并置 `BLOCKED`；**禁止**任何形式的验证码识别、打码或流量伪装（见 20.9）」。

- 删了什么：无（原条款文字全部保留）。
- 加了什么：为「跳登录」单独开一条**有上限、可审计**的自愈前置步骤。
- 为什么：自动登录生效后「跳登录」不再等于必须人工；但仍须守住「不得自动绕过」——故自愈**受限且失败即熔断**，绝不循环重试。

#### 20.2.2 红线 C3（不做反检测伪装）—— **不修订，整条保留**

**原条款原文**（§3.3）：「**不做反检测伪装**：不轮换 UA、不用代理/IP 轮换、不注入脚本对抗指纹、**不伪造或逆向 `anti-content`**」；落地要求：「技术选型中显式排除相关库（Crawlee proxy rotation、undetected-chromedriver、puppeteer-stealth 等）」

**修订后条款**：**原文不动**，并**追加一条对本决议的约束**：「凭据托管与自动登录**不得**以『更像真人』为理由引入任何伪装手段；自动登录的失败一律回落人工（20.4），不以伪装规避风控。」

- 删了什么：无。
- 加了什么：只加一句「自动登录不得借机触碰伪装」。
- 为什么：本次修订的边界是「**谁能完成登录**」，**不是**「如何骗过风控」；不加此约束，凭据托管极易被当成反检测的借口。

#### 20.2.3 红线 C5（数据不落 Git、脱敏存放）—— 修订（扩充范围）

**原条款原文**（§3.3）：「真实业务数据（运单号 / 收件人 / 手机号 / 地址）不落 Git，按 db.md 规范脱敏存放」；落地要求：「采集端日志脱敏、异常堆栈不打印响应体；Git 内仅占位符」

**修订后条款**：将**凭据明文**与**凭据密文**一并纳入本红线管辖范围：
- 红线：真实业务数据……**以及平台登录凭据（明文与密文）**不落 Git，按 db.md 规范脱敏存放。
- 落地要求：追加「**明文零落地**（不落盘 / 不入日志 / 不入响应 / 不入崩溃转储 / 不入 Git）；密文仅存采集端专用账户私有目录且 ACL 收紧」。

- 删了什么：无。
- 加了什么：把「凭据」显式写进「不落 Git / 脱敏」的管辖对象，并新增「明文零落地」硬要求。
- 为什么：原 C5 只覆盖业务数据；凭据托管若不明确纳入，实操中会出现「业务数据很小心、密码随手 log」的落差。

#### 20.2.4 ADR-C02（采集账号归属）—— 修订

**原条款原文**（§13.1）：
- 决策：「使用站长自有账号；采集端**不代管凭据**，仅附着人工已登录的浏览器上下文。」
- 备选：「……由系统代管站长密码自动登录（凭据托管，安全后果不可接受）——均不选。」

**修订后条款**：
- 决策：「使用站长自有账号**不变**；在站长**书面授权**且满足 20.2.9 全部生效条件的前提下，采集端**加密托管该账号的平台登录凭据**，用于本站自动登录与续登；未授权站点仍按原方式运行（仅附着人工已登录上下文）。」
- 备选：「由系统代管站长密码自动登录 → **由『不选』改为『有条件采纳』**（条件 = 20.2.9）。」

- 删了什么：删除「不代管凭据」的一刀切表述、删除「凭据托管安全后果不可接受」的定性结论。
- 加了什么：把「凭据托管」从「不可接受」改为「**有硬前置条件的可选项**」，并把账号归属（站长自有）保留为不可动摇的前提。
- 为什么：用户决议即选前者；但保留「账号必须来自站长自有」是为了守住红线 C1 与越权边界。

#### 20.2.5 ADR-C05（登录态方案）—— 修订

**原条款原文**（§13.1）：
- 上下文：「凭据不能托管；浏览器自动头（Cookie/UA/Referer）不可自行复现。」
- 决策：「CDP 连接**本方案专用**的浏览器实例（借 BrowserForce 思路）；该实例由**人工完成登录**，采集端不自行托管登录态。」
- 澄清：「……两者区别在「**谁完成登录**」：**人工登录 = 采纳；程序自动登录 = 排除**。」
- 备选：「程序代管站长密码并自动登录（凭据托管，安全后果不可接受）→ 不选」

**修订后条款**：
- 上下文：「浏览器自动头（Cookie/UA/Referer）不可自行复现；凭据托管**仅在已授权站点**可用。」
- 决策：「CDP 连接**本方案专用**的浏览器实例**不变**；该实例的**首次登录建议人工完成**（用于建立持久化 profile 与验收基线），此后在已授权站点可由**凭据托管自动登录/续登**；采集端托管的是**登录凭据**，登录态本身仍落在浏览器 profile 中，采集端不另行落盘登录态。」
- 澄清（改写）：「区别不在『谁完成登录』一律，而在『**是否有站长书面授权 + 是否满足 20.2.9 生效条件**』：满足 → 自动登录可用；不满足 → 回落人工登录。」
- 备选：「程序代管站长密码并自动登录 → **改为有条件下选**（见 ADR-C02 修订）。」
- **保留**：§18.3 补丁 3（必须用 `browser.contexts[0]` 复用登录态；多账号 = 每账号独立实例/profile）**原样保留**，且自动登录产出的登录态**必须**落在同一专用持久化 profile 的 `contexts[0]`。

- 删了什么：删除「采集端不自行托管登录态」中会把自动登录一并排除的表述；删除「程序自动登录 = 排除」的绝对口径。
- 加了什么：新增「首次人工、后续可自动」的分层，以及「登录态仍留在 profile、采集端不落盘登录态」的边界。
- 为什么：保留 CDP 附着的全部安全收口（§10.2.1）与补丁 3，是保证「自动登录不把原有安全设计推翻」的关键。

#### 20.2.6 §10.2（凭据不落地）—— 修订

**原条款原文**（§10.2 表）：

| 项 | 原表述 |
| ---- | ---- |
| 平台登录态 | 「**由人工在真实浏览器中完成登录**；采集端不代管账号密码、不保存密码、不自动登录」 |
| 平台凭据 | 「无（不采集密码）。浏览器 Cookie / `etag` / `pdd-id` 留在浏览器自身存储中，**采集端不落盘、不回传服务端**」 |

### 20.3 凭据托管设计（安全为第一目标）

#### 20.3.1 加密存储：Windows DPAPI

**作用域对比（依据 Microsoft 官方文档 CryptProtectData / CryptUnprotectData，来源见本章末）**

| 维度 | CurrentUser（默认，`dwFlags=0`） | LocalMachine（`CRYPTPROTECT_LOCAL_MACHINE`） |
| ---- | ---- | ---- |
| 可解密主体 | 只有**与加密时相同的用户凭据**、且在**同一台机器**上才可解密 | **该机器上的任意用户**都可用 `CryptUnprotectData` 解密 |
| 与本方案的契合 | 与 §10.2.1「专用 Windows 账户 + 目录 ACL 收紧」一致，暴露面最小 | 把解密面扩大到该机所有账户，与本方案「最小暴露面」原则冲突 |
| 结论 | **建议采用 CurrentUser 作用域** | 不采用 |

**取舍理由**：
- 采集端 daemon 与专用浏览器实例**运行在同一专用本地账户**下（§10.2.1 已定），CurrentUser 作用域对该账户可正常解密，满足需求；
- LocalMachine 会让任何在该机上登录的账户（含运维/临时账户/被入侵账户）解出**全部站长凭据**——这正是 K18 要压制的风险，故不用。

**其它已确认事实与用法（官方）**：
- DPAPI **不负责存储**：应用必须自行保存密文（opaque BLOB）；
- 支持可选**附加熵**（`pOptionalEntropy`）：加密用的熵必须在解密时**原样提供**。**存疑**：熵本身若也存于同机同账户，仅提高门槛、不改变威胁模型；**建议一期不引入**（精简优先），如需引入须先定「熵存放位置」并重新评估；
- 密文自带**完整性校验（MAC）**，可检出篡改；
- **失效场景（重要）**：若管理员**重置**（而非更改）该账户密码，之前加密的数据可能**不可恢复**（除非有恢复代理/备份密钥）→ 须写入运维手册（见 20.3.2 吊销流程与 K21）；
- PromptStruct 相关流程已被官方标记**弃用并将在 2027 年 2 月移除** → 本方案**一律传 NULL**，不启用交互式提示（与无人值守一致）。

> **实现绑定（存疑）**：Python 侧 DPAPI 通常经 `pywin32` 的 `win32crypt.CryptProtectData` / `CryptUnprotectData` 调用（社区资料显示 `CRYPTPROTECT_LOCAL_MACHINE = 0x4`）。**该绑定的函数签名、异常与常量取值须以 pywin32 官方文档复核**，不得凭记忆写死；实现前并入 V20 验证。

#### 20.3.2 凭据生命周期

| 阶段 | 谁 | 何时 | 动作与约束 |
| ---- | ---- | ---- | ---- |
| 写入 | 站长本人（或运维在站长在场/持授权时） | 授权归档且 20.2.9 生效条件满足后 | 经**采集端本地受控入口**输入（**不经服务端**）；立即 DPAPI 加密落密文；记审计（不含明文） |
| 读取 | 仅 L3 自动登录模块 | 仅在需要自动登录/续登时**即时解密** | 用后立即清零释放；**不缓存、不长驻**；不跨模块传递 |
| 轮换 | 站长本人 / 运维 | 站长改密，或登录失败分类判为「凭据错误」时 | 经同一受控入口重写密文（覆盖旧密文）；记审计；轮换前不删除授权 |
| 删除 / 吊销 | 运维（受主智能体审批）/ 系统 | 授权撤回、站长离职、集中机退役 | 密文**物理删除**；同步停用该站采集（20.6.3）；记审计；删除后不可解密旧密文 |

> **与 §10.2.1 的关系**：密文目录位于专用账户私有目录（示例占位：`%LOCALAPPDATA%/<采集端>/secrets/<station_code>.bin`，**文件名不含账号等敏感信息**），ACL 仅授权该专用账户。

#### 20.3.3 明文零落地（硬约束）

| 载体 | 约束 | 落地措施（可检查） |
| ---- | ---- | ---- |
| 不落盘 | 明文不写入任何文件（临时文件亦不可） | 只在内存解密；写文件路径一律走密文 |
| 不入日志 | 任何日志不得出现明文 | **全局强制**脱敏过滤器，覆盖采集端全部输出（含第三方库如 Playwright 的输出）；默认脱敏键：`password/passwd/pwd/smsCode/verificationCode/cookie/set-cookie/authorization/anti-content/etag/pdd-id`；抽查验证 |
| 不入响应 | 凭据永不进入 `/api/v1/crawler/*` 请求或响应 | 服务端零凭据；接口出参审查 |
| 不入崩溃转储 | 崩溃转储可能含进程内存明文 | 关闭/限制采集端进程的 dump 采集（Windows 错误报告策略）；**存疑，需实测** WER/dump 策略与转储内容（V22） |
| 不入 Git | 密文目录与任何凭据样例不入仓库 | `.gitignore` + 提交前扫描（沿用规划 §14.5 禁止项） |

> **存疑（内存明文）**：Python 侧字符串不可变，解密后的明文难以确定性地清零；建议以 `bytearray` 承载并及时覆盖，但**无法保证**不被 GC 复制或被系统换页。DPAPI 另有 `CryptProtectMemory`（进程内内存保护），是否引入**待评估**，并入 V22。

#### 20.3.4 凭据边界（与 API Key 的隔离）

| 项 | 平台登录凭据 | 采集端 API Key |
| ---- | ---- | ---- |
| 用途 | 登录**目标平台**（L3） | 认证**本系统服务端**（L1 通信，ADR-C20） |
| 存放 | 专用账户私有目录，DPAPI 密文，**逐站点一条** | 采集端本地加密文件 + 服务器配置（§10.2 原约定不变） |
| 使用者 | 仅 L3 自动登录模块 | 仅 L1 通信客户端 |
| 复用 | **禁止**与 API Key 混存、互借、互相派生 | 同上 |
| 是否随授权撤回删除 | 是（20.6.3） | 否（属采集端自身凭据） |

> 边界口径：采集端**只持有平台登录凭据**，不持有业务数据以外的任何其它凭据；ADR-C20 的**双认证**（管理端 JWT + 采集端 API Key）**不变**。

### 20.4 自动登录设计

#### 20.4.1 登录方式枚举与可行性

> 目标站点登录页实测观测到三种方式：**短信登录 / 密码登录 / 微信登录**（含「手机号 + 验证码」形式）。下列可行性为当前判断，**未实测项已标注**。

| 方式 | 观测事实 | 自动登录可行性 | 处置 | 状态 |
| ---- | ---- | ---- | ---- | ---- |
| 短信验证码 | 存在「手机号 + 验证码」 | 不可（验证码由平台下发，须人工获取） | **回落人工**（保留为人工兜底登录方式） | 已观测 |
| 账号密码 | 存在密码登录 | 唯一可能支持无人值守的方式；**是否叠加图形验证码/滑块/设备核验未实测** | 自动登录主路径，**失败即回落人工** | 部分未实测 |
| 微信登录 | PC 端通常为二维码扫码 | **是否真为扫码、会话有效期、能否重新扫码续期——均未实测** | 登记 V17；作 P0-06 兜底通道之一（扫码转发） | **未实测** |

#### 20.4.2 自动登录流程

```text
任务前 probeLogin() 失败
  ↓ 触发会话自愈（每站每任务 ≤ 1 次，拟）
从 DPAPI 密文解密凭据（仅内存，逐站点一条）
  ↓ 在同一专用持久化 profile 的 contexts[0] 打开登录页（不得 new_context()，§18.3 补丁 3）
按语义识别登录方式（按 DOM 文本/表单语义，不按索引，纪律同 K5）
  ↓ 填充账号密码 → 提交（由页面自身提交流程完成，不构造请求、不碰签名）
等待跳转/接口信号 → probeLogin() 复核
  ↓ 结果分类（见 20.4.3）
无论成败：内存凭据立即清零
```

- **合规边界**：提交动作走**页面自身的登录流程**，采集端不自造 HTTP 请求、不接触 `anti-content`（红线 C3 + ADR-C04）。
- **与 §18.3 补丁 3 的衔接**：自动登录**必须**落在**同一专用持久化 profile** 的 `browser.contexts[0]`，使登录态可由 CDP 附着直接复用；禁止为「隔离」而 `new_context()`。多账号 = **每账号独立浏览器实例/profile**（各自 `contexts[0]`），而非同一实例内多 context。

#### 20.4.3 失败分类与回落策略

| 失败类型 | 判定 | 处置 |
| ---- | ---- | ---- |
| 图形验证码 / 滑块 / 短信二次验证 / 设备核验 | 登录页出现挑战控件 | **必须回落人工**；**禁止**自动识别、打码或绕过 |
| 账号锁定 / 异常提示 / 异地风控提示 | 页面明确提示 | **必须回落人工**；记录风控事件（20.6.2） |
| 凭据错误 | 明确「账号或密码错误」 | 不重试；通知站长**更新凭据**（20.3.2 轮换） |
| 登录页结构突变（无法识别登录方式） | 关键 DOM/文本缺失 | **回落人工**；按结构突变处理（对齐 K5/K4） |
| 网络/超时等可恢复错误 | 非挑战类 | 受 ADR-C14 重试规则约束（≤2 次退避） |

**回落动作**：任务置 `BLOCKED`（沿用 ADR-C17，属「必须人工介入」的终止态）+ 告警触达「**能上机的人**」+ 启用人工兜底通道（20.4.4）。
**红线**：**禁止**任何形式的自动绕过、第三方打码、人工打码外包（见 20.9）。

#### 20.4.4 登录态维持与自愈

| 项 | 约定 |
| ---- | ---- |
| `probeLogin()` 时机 | 每次任务前；关键页面跳转后；心跳周期内的轻量抽查（拟） |
| 失效检测 | 跳登录页 / 接口返回未登录 / 关键 DOM 缺失（按语义判定） |
| 自愈触发 | `probeLogin()` 失败 → 走 20.4.2 流程；上限每站每任务 ≤ 1 次（拟，未实测） |
| 自愈失败 | 置 `BLOCKED` + 告警；**不自动重试**、**不循环** |
| **人工兜底通道（保留两条，作 P0-06 兜底、非主路径）** | ① **二维码转发**给站长（前提：目标站点支持 PC 扫码登录 → V17）；② **Windows 远程桌面/RDP**（受控通道，受 §10.2.1 约束） |

> 定位说明：自动登录**成功时**为主路径；**失败时**上述人工通道是兜底。P0-06 的任务定位由「唯一恢复手段」降级为「兜底通道验证」（见规划 P0-06 回填）。

### 20.5 自动化登录带来的风控影响

**如实分析**：
- 自动登录的行为特征（固定机器、固定时段、无真实交互轨迹）**比人工登录更易被识别**；本方案**仍不做任何伪装**（红线 C3），故该风险只能通过「失败即回落人工 + 不循环重试」收敛，**不能**通过伪装消除。
- 因此自动登录的**收益**是「减少人工介入频率」，**不是**「消除人工介入」——必须以 20.4.3 的回落机制为前提。

**对既有参数的影响判断**：

| 既有参数 | 是否调整 | 依据 |
| ---- | ---- | ---- |
| ADR-C14 请求间隔下限（暂定 ≥3s） | **暂不调整** | **未实测**：暂无「自动登录是否改变风控敏感度」的数据，不基于猜测改容量杠杆；登记 V19 后按实测决定 |
| ADR-C14 熔断后强制降频 | **不变，继续适用** | 自动登录失败/触发挑战即按 C2 熔断，熔断后降频再启 |
| §19.6 导出通道限频 | **暂不调整** | **未实测**：导出与登录方式无直接关系；登记 V19 观察是否需耦合 |

**判断口径**：**先观察、后调参**；在 V19 给出实测前，**不得**以「自动登录更快/更频繁」为由放宽任何限速。

### 20.9 明确不做清单（强制）

> **本次红线修订不包括下列任何一项**；每项绑定对应红线/条款，用于代码评审与依赖清单审查时逐条核对。

| # | 不做项 | 绑定红线/条款 |
| ---- | ---- | ---- |
| 1 | 验证码 / 滑块**自动识别**与**第三方打码**（含人工打码外包） | 红线 C2、C3 |
| 2 | 指纹伪装（含 stealth / undetected / 指纹对抗库） | 红线 C3 |
| 3 | UA 轮换 | 红线 C3 |
| 4 | 代理 / IP 轮换（含 proxy rotation 库） | 红线 C3 |
| 5 | `anti-content` 签名逆向（自行构造请求、破解签名） | 红线 C3、ADR-C04 |
| 6 | mitmproxy 中间人解密（安装根证书做 TLS 解密） | 红线 C3、C5、ADR-C04 |
