### 1.2 维度 2 · 边界合理性

- **范围清晰、可判定：** §0.2 六条自我约束 + §6.1「本次不做」10 项（含换组件库、重做视觉、改信息架构、引 ECharts、首屏性能专项、暗色、i18n）边界明确，无夹带。

- **跨工程边界（关键）：** 方案 §0.4 正确指出 `hrm-demo/src/pc/main.js:22` 只读复用 `hrm-admin` 基座，改 `hrm-admin/src/styles/**` 会**同时影响 Demo PC**（风险 R1）。此判断成立——已核实该 import 顺序为 `@admin/styles/index.scss` → `./styles/tokens.scss` → `element-overrides.scss`，故 admin 基座改动在 Demo 侧仍被后置 Token 覆盖。
- **与项目规则 §12.1 的关系（需更正表述）：** `项目规则1.md:400` 的硬约束是「**Demo 不得改动 `hrm-admin`/`hrm-server`**（Demo 只经 `@admin` 只读引用，删除 `hrm-demo` 即可完全回滚）」，**并非**「`hrm-admin` 不得被改动」。`hrm-admin` 属生产工程，可改但**须主智能体 Review**（`项目规则1.md:283`）。故方案附录 B 的事实性纠正方向**正确**：`demo-ui-redesign.md` §9.3 D-4（第 1559 行）"硬约束禁止改动 `hrm-admin`"属**表述过宽**，应修订为"Demo 不得改动 `hrm-admin`"。
- **遗留边界风险：** 方案把「`hrm-admin` 换色」列为批次 A 必做，但未声明该变更是否会改变**一期已验收/冻结页**的视觉（`demo-ui-redesign.md:131` 列出一期冻结页被动继承 PC Token）。换色会波及相关页 → 属生产可见变更，需用户/主智能体确认（见必改项 2）。

**必改项 1（阻塞批次 A 的 admin 部分）**
- 问题：R-0 兜底路径不闭合。必做-5.1 建议"取值直接对齐 Demo 已验证值"，即把 `#0958D9` 等字面量写入 `hrm-admin/src/styles/index.scss`（方案 §5 表末行"归口见 R-0"，选项③）；但同一方案 R5-3 规定"`src/**` 出现十六进制字面量仅允许在 `tokens.*.scss` 内"，而 `hrm-admin` **无 tokens 文件**。两处自相矛盾，A5-5（"`hrm-admin/src` 无未登记的字面量色值"）的"登记"载体亦未定义。
- 验收标准：方案明确以下其一并写入正文——(a) 例外条款：允许 `hrm-admin/src/styles/index.scss` 承载字面量，并指明"登记"载体（何处登记、由谁登记）；或 (b) 在 `hrm-admin` 新建 `styles/tokens.scss`（此时 R5-3 措辞须同步）。同时明确"R-0 未裁定前，批次 A 仅可实施 Demo 侧（`PageState`/安全区/焦点环），`hrm-admin` 换色暂停"。
- 复核方式：读方案 §5 与 §1.5 R5-3/A5-5，核对是否给出唯一、无冲突的落地载体。
- 阻塞：**是**（`hrm-admin` 换色为 P0 合规项，路径不闭合即无法开工）。

**必改项 2（阻塞 admin 换色决策）**
- 问题：生产端主色变更缺替代方案对比与决策归属。必做-5.1 将 `hrm-admin` 主/功能色整体换为 Demo 700 档（如 `#409EFF`→`#0958D9`），属生产可见视觉变更；方案 §0.2 自约束"不重做视觉风格"与之形成张力，且未论证替代方案（加深色 vs 深色文字/描边），亦未声明该变更属产品/视觉方向、需用户确认（`项目规则1.md` §11.4 口径与产品决策归用户）。

- 阻塞：**是**（决策未定则换色不可落地）。

## 3. 特别裁定项独立判定（R-0～R-3）

> 以下为本评估方的独立判定，非替方案决策（决策归主智能体/用户）。

### R-0 · Token 真源归口

- **"生产不得依赖演示工程"——成立。** 事实核查：当前 `hrm-demo/src/pc/main.js:22` 单向只读引用 `hrm-admin` 基座，Token 真源在 `hrm-demo/src/shared/styles/tokens.base.scss`；要修 `hrm-admin` 对比度，必须有 **admin 侧**的落地载体。方向正确。
- **把真源上移到 `hrm-admin` 是否属结构变更、是否须走架构师 ADR——是，须走 ADR。** 理由（波及面）：

  2. `verify:tokens` 脚本现扫 `hrm-demo` 的 `pc/styles/tokens.scss`（`scripts/gen-element-tokens.mjs` 读取目标），真源上移会改动门禁扫描路径；

  4. 影响 Demo 三入口构建与 e2e。
  属 C 档结构变更 → **须架构师出 ADR，交主智能体裁定**；该 ADR 若产出，须**另行**经本角色评估（本次结论不覆盖）。
- **批次 A「局部值覆盖 + `TODO(扩展)`」是否足够——仅可作限定期合规兜底，不足以收尾。** 除必改项 1（与 R5-3/A5-5 冲突）外，还须：① 补待核实"admin 加变量后 Demo 覆盖顺序仍成立"（风险 R1 的可判定断言）；② 换色须用户确认（必改项 2）。
- **建议：** 采纳方案的"先③兜底 + 同步启动①的 ADR"路线，但必须在方案中写清"③ 为临时、① 为目标态的收敛期限由主智能体裁定"。

### R-1 · 是否为 `hrm-admin` 补最小门禁

- **独立判定：补 lint 为"建议项"，非本次方案的充分必要条件；但"指向 `hrm-admin` 的 Playwright 配置"为必做。**
- 依据：`hrm-admin/package.json` 确无 lint/verify（已核实）；但方案对 `hrm-admin` 的验收 A1-5/A5-1 依赖浏览器断言，Playwright 可驱动 served build，故"无法自动化"不成立（见必改项 6）。
- 结论：① 补 `lint` 需装 eslint 依赖 → 属 B 档依赖安装，由主智能体裁定是否纳入本批次；② 无论是否补 lint，**必须**新增对 `hrm-admin` 的 Playwright config/baseURL，否则 A1-5/A5-1 的 `hrm-admin` 部分不可执行。

### R-2 · 移动端 `user-scalable=no` 能否放开

- **独立判定：不能凭空结论，须先核实后裁定。** 约束实在 Android H5 壳 WebView。判定所需核实项：
  1. `hrm-android-shell` 侧 WebView 配置：`setSupportZoom` / `setBuiltInZoomControls` / `setUseWideViewPort` / 是否 `setInitialScale`（决定去掉 meta 后壳内是否仍禁缩放）；
  2. 目标 WebView/Android 版本与 `minSdk`（决定 `env()`/`max()`/`viewport-fit` 支持，亦影响 R6-1）；
  3. 使用面：`mobile.html` 是否仅壳内使用，还是也用于浏览器/PWA/扫码演示（后者则 `user-scalable=no` 直接构成 SC 1.4.4 违规）；
  4. 现状 480/640 兜底布局在 200% 文本放大下的回归面（刘海/横屏/固定栏）。
- 判据（先给口径，不先给结论）：SC 1.4.4 要求文本可放大至 200% 且不丢内容；若目标环境含浏览器访问，`user-scalable=no` 即违规，应放开；若严格仅壳内且壳本身禁缩放，则应【放开 meta + 在壳侧保留禁用】或【维持现状登记为已知偏差】，二选一须留决策记录。
- 建议：把 R-2 由"裁定项"降为"待核实 → 再裁定"，并在 §7.2 补齐上述核实方法（现仅有方向性一句）。
