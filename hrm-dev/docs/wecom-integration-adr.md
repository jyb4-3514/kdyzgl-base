### 3.1 由能力边界得出的关键结论（ADR 必须正面回答）

1. **在「不采购付费接口 + 不逆向不注入」的双重约束下，官方通道无法读取群消息。** 三条官方免费通道（群机器人 Webhook / 自建应用回调 / 官方 CLI）**均未提供读群消息能力**（前两者官方明确否定，后者未声明）。
2. 因此用户选择的「桌面端旁路读取群消息」是**当前约束下唯一的可能路径**，但它的**可实现性目前是未验证假设**，不是已成立事实。
3. **这意味着需求 G1 与 G2 存在根本性风险**：若桌面端旁路被 POC 判定为不可行（既不暴露调试端口、UI Automation 也取不到消息文本），则 G1/G2 **在本轮约束下无解**，必须回到「采购会话内容存档」或「放弃自动化读取、改人工录入」二选一。
4. G3/G4（发送）风险显著低于 G1/G2：群机器人 Webhook 的发送能力是**官方免费且已核实**的；仿人工发送的可行性依赖同一套 UI 自动化能力，与 G1 共享前提。
5. **需求可解耦**：G4 的「客户群取件通知」可**先只走群机器人 Webhook**（不依赖未验证的旁路能力）落地；G1/G2/G3 与「个人微信 1 对 1」强依赖桌面端旁路，须待 POC 结论。

### 4.3 群内「工单」消息的约定格式（先定义，再解析）

**约定（拟，需与用户确认 → Q8）**：群内工单消息采用**固定模板**，以关键字起始，字段用固定分隔符：

```text
[工单] 驿站=<station_code> 类型=<异常类型> 运单号=<占位> 手机号=<占位后4位> 描述=<一句话> 期望=<YYYY-MM-DD HH:mm>
```

| 项    | 约定                                                      |
| ---- | ------------------------------------------------------- |
| 起始标识 | 消息首行以 `[工单]` 开头（可配置）                                    |
| 字段分隔 | 半角空格 + `键=`（键名固定枚举，顺序不敏感）                               |
| 兜底   | 含「退件/破损/无人取/超期未取」等关键字但**不符合模板** → 进「待办池」，人工确认后转工单       |
| 降级策略 | 见 8.3                                                   |
| 脱敏   | 手机号在群消息中**只接收后 4 位**；服务端落库仍按 `DesensitizeUtil` 全量脱敏规则处理 |

> **为什么先定义格式**：群内消息格式不可控是解析稳定性的最大变量。把「格式」变成**双方约定**（告知站长/客服按模板发，或由系统生成模板供复制），可把「自然语言理解」问题降级为「结构化解析」问题，避免引入不可验证的 NLP 组件。**若用户不接受约定格式**，则只能走「人工确认 + 待办池」兜底，G2 的自动化程度将大幅下降（→ Q8）。

| **T1 群机器人 Webhook**          | S3 客户群通知（**外部群支持性未验证** → V24） | **≤20 条/分钟/机器人**（已核实）              | HTTP 非 200；`errcode` 非 0（如 40058 超长、限频类错误码） | **较高**：有明确 HTTP 状态 + `errcode` | **S3 主用**（外部群支持性确认后启用）         |
| **T2 采集端仿人工发送**              | S2 工单回帖、S4 个人微信通知、S3 兜底       | **无官方承诺** → 必须自行设保守限频（见 14.1 W-C5） | UI 层失败（发送按钮不可用、出现失败标记、输入未生效）——**不可靠**       | **低**：只有 UI 现象，无回执             | **S2/S4 唯一路径**（未验证），必须配人工确认闸门  |
| **T3 腾讯官方 CLI（`wecom-cli`）** | 机器人最近对话过的单聊/群聊主动推送            | 未声明                                | 依赖 CLI 自身错误输出                               | 中                              | **长期替换候选**，本轮不接入；仅登记为「通道可替换」目标 |

> **三方都拿不到真正的「已送达」回执**：T1 只到「官方受理」，T2 只到「本机客户端显示已发出」，T3 README 未声明回执。**「已送达」在本轮约束下不可强求**（见第 10 章）。

### 5.3 选型结论

1. **读取**：**R1 与 R2 并列进入 POC**，以 POC-01 / POC-02 的实测证据二选一（或组合：R1 取文本、R2 做兜底定位）。**R1/R2 均不通过时，G1/G2 无解**，须回退 Q7 决策。
2. **发送**：S3 主用 T1（群机器人 Webhook）；S2/S4 只能走 T2（仿人工，未验证）；T3 作为长期可替换通道。
3. **架构上必须做到「通道可替换」**：读取与发送各设一层通道抽象（见 15.3），使 R4（付费）、T3（官方 CLI）未来接入时**不推翻现有编排、落库、状态跟踪与前端**。

### 6.1 分层架构（文字化架构图）

### 6.2 各层职责与关键约定

| 层          | 职责                                     | 明确不做                             |
| ---------- | -------------------------------------- | -------------------------------- |
| W-L1 控制与编排 | 任务生成、优先级、限频闸门、人工确认闸门、落库幂等、状态跟踪、审计、一键停用 | 不持有企微登录凭据（除非 §20 硬前置满足）；不直接操作客户端 |
| W-L2 通道抽象  | 发送通道统一接口与结果映射                          | 不含具体通道实现细节；不感知采集端 UI 细节          |
| A-L1 守护进程  | 常驻、看护、心跳、任务领取、配置热加载、本地熔断               | 不解析业务语义（保持「薄」）                   |
| A-L2 结构适配  | 企微客户端改版隔离（规则集版本化）                      | 不含通道机制逻辑                         |
| A-L3 读取通道  | 会话枚举、增量读取、去重键                          | 不控制发送；不落库（交 A-L6）                |
| A-L4 发送通道  | 仿人工输入与发送、UI 结果采集                       | **不碰协议、不注入、不读内存**（W-C1）；不自行放宽限频  |
| A-L5 限频熔断  | 令牌桶/漏桶、优先级、退避、熔断                       | **不提供自动绕过捷径**；熔断后只能人工确认恢复        |
| A-L6 上报    | 脱敏、批量上报、结果回执                           | 不直连数据库（只调 `/api/v1/wecom/*`）     |

**依赖方向单向**：W-L1 → W-L2；A-L1 → A-L2 → A-L3/A-L4 → A-L5 → A-L6。**A-L5 为强制经过层**，任何读取/发送动作不得绕过。

### 6.3 关键约定

| 项            | 约定                                                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 认证           | 服务端双体系沿用二期：管理端 JWT（`Authorization: Bearer`）+ 采集端 API Key（`X-Wecom-Key`，与 `X-Crawler-Key` 并列且**互不复用**；密钥仅存服务器配置与采集端本地加密文件）                              |
| Redis Key    | 新增前缀 `wecom:`，与 `hrm:` / `crawler:` 隔离。拟：`wecom:lock:notify:{task_id}`、`wecom:rate:{channel}:{scope}`、`wecom:heartbeat:{node_code}`、`wecom:killswitch` |
| 服务端不主动连入     | 采集端**出站轮询**（拉模式），采集端无公网入站要求                                                                                                                            |
| 采集端保持「薄」     | 群白名单、模板、限频参数、确认闸门策略、结构适配规则**全部服务端下发**（版本化，热加载）                                                                                                         |
| 只读 + UI 动作边界 | 读取仅「读取 UI/可访问性树/旁路响应」；发送仅「在官方客户端 UI 上模拟人工输入与点击」。**不构造任何网络请求**（W-C1）                                                                                    |
| 幂等           | 群消息：`(node_code, group_id, msg_dedupe_key)`；通知任务：`(biz_type, biz_id, target_id, template_id, content_hash)`                                            |

### 6.4 端到端时序（S1 工单识别 → S2 完结回帖）

```text
【采集端】A-L1 轮询领取「群监听」配置（群白名单 + 轮询间隔）
   ↓
【采集端】A-L3 读取通道：枚举会话列表 → 定位白名单内的目标群
   ↓  按增量游标（上次最大消息序号/时间戳）读取新消息
【采集端】消息结构化：命中 [工单] 模板 → 生成结构化对象 + 去重键
   ↓  未命中模板但命中关键字 → 标记 needs_manual=true（进待办池）
【采集端】A-L5 限频 → A-L6 上报 POST /api/v1/wecom/messages/report
   ↓
【服务端】W-L1 幂等去重 → 落 wecom_message → 命中工单模板则创建/关联工单
   ↓  needs_manual=true 则进人工待办池（前端可见）
（工单在系统内处理，状态流转到「已完结」）
   ↓
【服务端】W-L1 生成「完结回帖」通知任务（biz_type=WORK_ORDER_CLOSED）
   ↓  若该通道或该群需人工确认 → 任务置 PENDING_APPROVE，等 PC/移动端确认
【服务端】W-L2 选定通道 = UiaAgentChannel（T2）→ 任务入优先级队列 → 限频闸门取令牌
   ↓
【采集端】A-L1 领取待发送任务 → A-L2 定位目标群 → A-L4 仿人工：聚焦会话 → 输入模板文本 → 触发发送
   ↓  采集 UI 结果信号（输入框清空 / 消息条目出现 / 失败标记）
【采集端】A-L6 回报 POST /api/v1/wecom/notify-tasks/{taskId}/result
   ↓
【服务端】状态机推进：SUBMITTED → DISPATCHED / FAILED →（重试）→ DEAD_LETTER
   ↓  全链路写审计；失败进人工兜底待办（S5）
```

## 7. POC 计划（未验证前提的编排）

> **性质**：把「读取通道是否可行」「是否暴露调试端口 / UI Automation 能否取到消息文本」「外部群 webhook 是否可推送」「仿人工发送的合规判定与可行性」四类未验证前提，编排为**限定范围、可独立判定**的 POC 任务。
> **纪律**：POC 阶段一律**只读优先**；涉及写动作（发送）的 POC 必须在**专用测试群**、**经用户明确授权**、**单次少量**执行，且全程留痕。POC 脚本本轮**不写**，仅给规格。POC 失败即按「失败判据」切路线，**不得**为通过而放宽约束。

| 编号         | POC 目标                             | 范围与最小做法                                                                                                                                             | **通过判据**                                    | **失败判据与切换**                                                       | 责任角色             |
| ---------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------- | ---------------- |
| **POC-01** | 企微 PC 客户端是否暴露 CDP 调试端口（决定 R1 可行性）  | ① 确认客户端技术栈（进程模块/资源目录是否含 CEF/Electron 特征）；② 尝试以 `--remote-debugging-port` 启动（**不修改安装目录**）；③ 访问 `http://127.0.0.1:<port>/json/version` 与 `/json/list` | 能列出 target 且能 attach；能读到会话列表相关 DOM/可访问性节点   | 无法启动或端口不可用 → **R1 不成立**，转 POC-02；若两者均失败 → G1/G2 无解，触发 Q7          | 架构师 + 后端工程师      |
| **POC-02** | UI Automation 能否读到群消息文本（决定 R2 可行性） | 用 pywinauto（`uia` 后端）遍历企微窗口：① 能否枚举主窗口与会话列表控件树；② 消息列表区能否取到消息文本、发送者、时间；③ 控件命名（`ControlType`/`Name`/`AutomationId`）是否稳定可复用；④ 记录树深度与节点数量级               | 能稳定取到**消息文本**与**会话名**，且两次冷启动后定位规则仍成立        | 只能取到窗口壳、取不到消息文本；或命名完全不稳定 → **R2 不成立**；若 R1 也不成立 → 触发 Q7           | 架构师 + 后端工程师      |
| **POC-03** | 外部客户群能否用群机器人 Webhook 推送（决定 S3 主通道） | 在**一个专用测试外部群**配置群机器人 → 用官方 webhook 发送一条 `text` 与一条 `markdown`；记录 HTTP 状态与 `errcode`                                                                 | 外部群中**成功收到消息**且 `errcode=0`                 | 外部群不支持群机器人 / 发送被拒 → S3 转 T2（仿人工，依赖 POC-04），并登记为能力缺失               | 后端工程师            |
| **POC-04** | 仿人工发送的可行性 + 合规判定（决定 S2/S4）         | ① 静态自查：进程无第三方模块注入、企微安装目录文件哈希前后一致、采集端无 `ReadProcessMemory` 调用（对照 14.2 判定标准逐条自检）；② 在**测试群/测试联系人**上由人工授权，执行**一次**「聚焦会话 → 输入 → 发送」并采集 UI 结果信号           | 全部判定标准通过 **且** 目标端确实收到消息 **且** UI 结果信号可稳定采集 | 任一判定标准不通过 → **方案合规不成立**，立即停止；UI 结果信号不可采集 → 状态跟踪只能退化为「已提交」（第 10 章） | 架构师 + 主智能体（合规判定） |
| **POC-05** | 群机器人限频与超长行为实测（决定限频参数）              | 在测试群按受控节奏发送：① 记录 ≥20 条/分钟时的实际表现与错误码；② 发送 >4096 字节 markdown，确认 40058；③ 记录成功/失败边界                                                                     | 得到可复现的限频边界与超长错误码，用于标定令牌桶参数与内容校验             | 行为与预期不符 → 参数按实测重标；**限频参数不得据猜测放宽**                                 | 后端工程师            |
| **POC-06** | 消息滚屏与虚拟列表的增量读取（R1/R2 通过后）          | 在目标群内构造 ≥200 条历史消息：① 观察消息列表是否为虚拟列表（只渲染可视区）；② 验证滚动加载能否取全；③ 验证「新消息」定位与增量游标可用性                                                                         | 能定义**稳定的增量游标**并保证不重复不漏读（在小窗口内可验证）           | 无法稳定增量（游标不可得/渲染丢帧）→ 改为「窗口内全量去重」策略，并下调自动化置信度（登记 K）                 | 后端工程师 + 测试工程师    |

**POC 与需求的对应**：POC-01/02/06 → G1/G2；POC-04 → G3/S4；POC-03/05 → G4/S3；POC-04 的判定标准 → 第 14 章合规红线。

## 8. 读取通道设计（对应用户问题 A）

### 8.1 通道选择与切换

| 项     | 内容                                                                                |
| ----- | --------------------------------------------------------------------------------- |
| 归属层   | A-L3 读取通道层，由 A-L1 装配注入                                                            |
| 主通道判定 | 依 POC-01 与 POC-02 结论：R1 通过则 **R1 为主、R2 为兜底**；仅 R2 通过则 **R2 为唯一通道**；两者皆不通过 → 触发 Q7 |
| 切换纪律  | 同一群同一时刻**只允许一个读取动作**（与 A-L5 限频闸门互斥），禁止双通道同读（沿用二期 §19.3「多通道并行同采无收益且放大风险」的纪律）       |
| 降级    | R1 连续 N 次取不到文本 → 切 R2 一次；再失败 → 该群置 `read_unhealthy`，**人工复核后解除**，禁止自动恢复            |

### 8.2 多工作群并发

| 问题    | 设计（拟）                                                                                             |
| ----- | ------------------------------------------------------------------------------------------------- |
| 枚举群列表 | 通过会话列表控件/节点枚举，取**群名 + 稳定标识**；只登记**白名单内**的群（其余一律忽略，不读取、不落库）                                        |
| 群标识   | 优先使用客户端可得的稳定标识（如会话 ID）；**若只能取到群名**，则以「群名 + 驿站绑定」作为弱标识，并登记为脆弱点（→ V25）                              |
| 切换群   | 按白名单逐群串行切换（受 A-L5 限频），切换后校验「当前会话 = 目标会话」再读取                                                       |
| 增量读取  | 游标候选：① 消息序号/时间戳（若无则退化为）② 上轮最后一条消息的**内容哈希**。二者择一，**幂等键 =** **`(node_code, group_id, dedupe_key)`** |
| 虚拟列表  | 列表若为虚拟列表（只渲染可视区），则「滚动 → 采集 → 去重」；**去重键必须与渲染无关**（稳定标识或内容哈希），否则会因丢帧漏读                               |
| 并发上限  | 单实例多群**串行**处理；组数上限由 POC-06 与资源实测标定（拟 ≤ 10 群/实例，未验证 → V26）                                         |

### 8.3 消息解析与降级策略

| 级          | 触发条件                                                    | 处置                                                               |
| ---------- | ------------------------------------------------------- | ---------------------------------------------------------------- |
| L1 结构化命中   | 消息符合第 4.3 章约定模板                                         | 直接结构化 → 创建/关联工单（`source=WECOM_AUTO`，沿用 Demo 既有 `AUTO_WECHAT` 语义） |
| L2 规则 + 正则 | 命中关键字但不符合模板                                             | 规则提取候选字段 + 正则兜底 → 生成**待确认工单草稿**                                  |
| L3 待办池     | 无法提取必要字段                                                | 进人工待办池，前端「企微待办」列表展示**脱敏摘要**，人工确认后转正式工单或废弃                        |
| 降级纪律       | 任何一级都**必须落** **`wecom_message`** **原文（脱敏后）**，保证可追溯与二次解析 | —                                                                |

### 8.4 幂等与去重键

| 对象   | 幂等键                                                                                             | 说明                                                    |
| ---- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 群消息  | `(node_code, group_id, dedupe_key)`，其中 `dedupe_key` = 平台可得的唯一标识，**不可得时**用 `hash(发送者 + 时间 + 文本)` | 优先用平台标识；哈希兜底会在「同一秒同一人发同样文本」时产生碰撞，**接受该误合并**并登记（→ V25） |

## 9. 发送通道设计（对应用户问题 B）

### 9.1 三条通路对比与选型

见第 5.2 章对比表。**选型**：S3 → T1（外部群支持性 POC-03 通过后）；S2/S4 → T2；T3 长期替换候选。

> **T1 外部群限制的说明（存疑）**：有资料称群机器人推送**仅支持内部群/上下游群**，不含外部客户群。该说法**未获官方文档确认**，且与「群机器人可用于客户群服务」的常见实践存在冲突 → **必须实测（POC-03 / V24）**，本文**不据此下结论**。

### 9.2 模板机制：如何保证「格式统一规范」在工程上不可绕过

| 机制         | 设计                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------- |
| **模板集中定义** | 模板只在服务端 `notify_template` 表定义（含 `code / 场景 / 通道适配体 / 变量声明 / 状态`）；**采集端与前端不得内联任何模板文本**         |
| **渲染层单点**  | 渲染**只在服务端发生一次**（`TemplateRenderer`），产出**最终文本**下发；采集端只负责「把这段文本打进输入框」                           |
| **发布校验**   | 模板启用前强制校验：① 变量声明与渲染调用一致；② 渲染后**长度 ≤ 4096 字节**（群机器人 markdown 上限，已核实）；③ 禁用变量占位符残留（如 `{{...}}`）  |
| **运行时校验**  | 下发前二次校验长度与占位符；超长即失败并置任务 `FAILED`（错误码 9708），**不得**静默截断                                         |
| **不可绕过性**  | 采集端接口**只接受已渲染文本**，不接受模板 code + 变量（否则采集端可自行渲染，形成第二渲染点）                                         |
| **约束**     | 群机器人仅 markdown/text；仿人工发送按客户端可粘贴文本处理（**是否支持 markdown 渲染未验证 → V27**，拟统一下发**纯文本 + 轻量排版**以兼容两通道） |

## 10. 通知模板与状态跟踪（对应用户问题 C）

### 10.1 送达状态的定义与采集（关键：区分「已提交」与「已送达」）

| 状态                   | 定义                                                             | T1 Webhook 能否拿到             | T2 仿人工能否拿到             | T3 CLI 能否拿到 |
| -------------------- | -------------------------------------------------------------- | --------------------------- | ---------------------- | ----------- |
| `QUEUED`             | 任务已入队                                                          | 是（本系统内部态）                   | 是                      | 是           |
| `SENDING`            | 正被通道取走处理                                                       | 是                           | 是                      | 是           |
| `SUBMITTED` **已提交**  | 通道**受理**了发送请求（T1 = HTTP 200 且 `errcode=0`；T2 = 文本已成功输入并触发发送动作） | 是                           | 是（较可靠）                 | 是           |
| `DISPATCHED` **已发出** | 本机客户端/通道侧显示消息已发出（T2 = 会话中出现该消息条目；T1 无此层）                       | 不适用                         | 是（**UI 现象，可靠性中等**）     | 未知          |
| `DELIVERED` **已送达**  | 接收方**确实收到**                                                    | **拿不到**（无回执）                | **拿不到**（无回执）           | **未声明（存疑）** |
| `FAILED`             | 明确失败                                                           | 是（HTTP 非 200 / `errcode≠0`） | 是（UI 失败标记 / 超时未出现消息条目） | 是           |
| `DEAD_LETTER`        | 重试耗尽                                                           | 是                           | 是                      | 是           |

> **硬性口径（对齐用户要求）**：
>
> 1. **HTTP 200 ≠ 已送达**；`errcode=0` 只代表**官方受理**。
> 2. 本系统**不提供**"已送达"承诺。产品层展示必须写明口径为「已提交 / 已发出 / 失败」，**不得**把 `SUBMITTED` 展示为「已送达」。
> 3. 若未来接入 R4（会话内容存档）或 T3 提供回执，则新增 `DELIVERED` 采集点，状态机向前兼容（见 15.3）。
> 4. **可验证的替代口径**：以「无失败信号 + 观察窗口内成功」作为**近似成功**，并在统计口径中明确标注「近似」（见 10.4）。

### 10.2 状态机设计（拟）

```text
QUEUED ──取令牌成功──▶ SENDING ──通道受理──▶ SUBMITTED ──观察窗口内成功──▶ DISPATCHED
  │                        │                     │                              │
  │                        │                     └──失败信号/超时──▶ RETRYING ──┐ │
  │                        └──通道不可用（熔断）──▶ FAILED                      │ │
  └──人工撤回 / 停用──▶ CANCELED                                                 │ │
                                                                               ▼ ▼
                                        RETRYING（≤3 次，指数退避）──耗尽──▶ DEAD_LETTER ──▶ 人工兜底待办
```

| 项      | 约定                                                                                 |
| ------ | ---------------------------------------------------------------------------------- |
| 合法流转   | 仅允许上图方向；非法流转返回 **9707**                                                            |
| 重试次数   | **≤ 3 次**（拟，未实测 → V28）；超限进 `DEAD_LETTER`                                           |
| 退避     | 指数退避 + 抖动；**不得**用重试绕过限频（每次重试必须重新取令牌）                                               |
| 幂等     | 幂等键 `(biz_type, biz_id, target_id, template_id, content_hash)`；命中即返回既有任务（错误码 9706） |
| 死信处理   | `DEAD_LETTER` 任务进「通知失败待办」，人工可重发或转其他通道；**禁止静默丢弃**                                   |
| 人工确认闸门 | `PENDING_APPROVE → QUEUED` 只能由**授权角色**触发（ADMIN / STATION\_ADMIN），且写审计              |

### 10.3 一键停用（本地 + 远端）

| 层       | 机制                                                    |
| ------- | ----------------------------------------------------- |
| 远端（服务端） | `wecom:killswitch` 全局开关 + 节点级开关；置位后**停止下发新任务**，在途任务终止 |
| 本地（采集端） | 托盘「立即停止」按钮 + 本地配置熔断位；置位后**立即停止读取与发送**，仅保留心跳           |
| 恢复      | **只能人工恢复**（本地托盘确认 + 服务端置位），沿用二期「熔断后禁止自动恢复」纪律          |

### 10.4 送达率指标口径与埋点

| 指标        | 口径                                      | 埋点位置        | 说明                      |
| --------- | --------------------------------------- | ----------- | ----------------------- |
| 提交成功率     | `SUBMITTED` 及以后状态数 / 进入 `SENDING` 的任务数  | 服务端状态机      | 反映通道受理能力                |
| 发出率       | `DISPATCHED` / `SUBMITTED`（**仅 T2 可算**） | 采集端 UI 结果回传 | T1 无此层                  |
| **近似送达率** | （`DISPATCHED` 且观察窗口内无失败信号）/ 总任务         | 服务端统计       | **必须标注「近似」**，不得宣传为真实送达率 |
| 失败率 / 死信率 | `FAILED` / `DEAD_LETTER` 占比             | 服务端         | 按通道、按驿站、按模板分组           |
| 人工确认积压量   | `PENDING_APPROVE` 任务数 + 最久等待时长          | 服务端         | 反映闸门是否成为瓶颈              |
| 限频命中次数    | 命中限频被推迟/拒绝的任务数                          | A-L5 + W-L1 | 反映限频参数是否偏紧              |

**埋点事件（全链路留痕，写入审计）**：任务创建 / 入队 / 取令牌（含是否超限）/ 人工确认（谁、何时、结果）/ 通道受理 / UI 结果(A-L4 采集) / 重试（第几次、原因）/ 死信 / 人工兜底处理。

### 12.2 错误码分段申请

**结论：申请独立号段** **`97xx`（拟** **`9701–9720`）。**

| 段                                | 归属                                          | 来源                                    |
| -------------------------------- | ------------------------------------------- | ------------------------------------- |
| 10xx / 20xx / 30xx / 40xx / 50xx | 认证账号 / 员工 / 部门 / 驿站 / 导入导出                  | `api.md` §2.1（已定）                     |
| 60xx / 70xx                      | 爬虫（同步任务）/ 包裹                                | `plan.md` §3.4（已定）                    |
| 80xx / 90xx / 91xx               | 工单 / 通知 / 考勤                                | `demo-design.md` §7.4（提案）             |
| 92xx / 93xx / 94xx / 95xx        | KPI / 人事 / 财务 / 同步任务自定义配置                   | SESSION-STATE M8 等（已落地）               |
| 96xx                             | 请假申请（M11）                                   | `demo-leave-design.md`（已占用 9601–9607） |
| **97xx（本文申请）**                   | **企业微信接入（采集端通信 / 群 / 消息 / 通知任务 / 停用 / 审计）** | 本文                                    |

**理由**：① 90xx（通知）是**系统内站内信/通知中心**语义，与「企微通道接入」关注点不同，混用会让「通知内容不存在」与「企微任务状态非法」难以区分；② 96xx 已被 M11 请假占用；③ 97xx 与既有「每新增业务域独占一段」的习惯一致，且与 60xx（采集端通信）形成「不同采集通道各自独立段」的对称结构（60xx 爬虫 / 97xx 企微）。

| code      | 含义                              |
| --------- | ------------------------------- |
| 9701      | 企微采集节点未注册或心跳超时                  |
| 9702      | 企微接口密钥（`X-Wecom-Key`）无效         |
| 9703      | 驿站未绑定企业微信配置                     |
| 9704      | 群未登记或不在白名单                      |
| 9705      | 群消息上报数据校验失败                     |
| 9706      | 消息/任务重复（幂等键命中）                  |
| 9707      | 通知任务不存在或状态不允许该操作                |
| 9708      | 通知内容超长（markdown > 4096 字节）或渲染失败 |
| 9709      | 发送通道不可用（熔断中）                    |
| 9710      | 人工确认未通过，禁止发送                    |
| 9711      | 命中限频上限                          |
| 9712      | 目标不在白名单（群 / 成员）                 |
| 9713      | 一键停用已激活                         |

## 15. 质量属性保障（对应二期 ADR §12 体例）

### 15.1 稳定性

| 风险来源              | 保障机制                                                    | 验证方式                  |
| ----------------- | ------------------------------------------------------- | --------------------- |
| 登录态失效             | 每次读取/发送前 `probeClient()`；失效即置 `BLOCKED` 并告警；**默认不自动重登** | 静置观察失效表现（→ V30）       |
| **客户端升级导致控件结构变化** | A-L2 结构适配层**规则集版本化**；结构突变即熔断 + 告警，**禁止自动猜规则**           | 升级前后对比走查；突变注入演练       |
| 多群并发资源占用          | 串行处理 + 群数上限；采样内存/句柄                                     | 长跑采样（→ V26）           |
| 长跑内存与句柄泄漏         | 心跳带 `memMb` / `handleCount`；超阈告警；必要时周期性重建读取会话           | ≥2h 长跑采样（沿用二期 V14 做法） |
| 单实例多群上限           | 由实测标定（拟 ≤10 群/实例，未验证）                                   | POC-06 + 容量核算         |

### 15.2 安全性

| 维度      | 机制                                                                   |
| ------- | -------------------------------------------------------------------- |
| 本地登录态保护 | 登录态**留在官方客户端自身存储**；采集端不落盘、不回传；若代管则走 DPAPI CurrentUser（对齐采集端 §20.3.1） |
| 通知内容脱敏  | 手机号 / 取件码在入库、日志、出参三处脱敏；日志**不打印全文通知内容**                               |
| 双向鉴权    | 采集端持 `X-Wecom-Key`；服务端不主动连入；密钥仅存服务器配置与采集端本地加密文件，不入 Git / 日志 / 响应     |
| 审计不可篡改  | `wecom_audit_log` 只增不改（应用层禁止 UPDATE/DELETE；数据库层权限收口待数据库工程师确认）        |
| 越权防护    | 全部写操作校验资源归属 `station_id`；非白名单返回 9704/9712                            |

### 15.3 可扩展性（通道可替换 + 改版隔离）

| 目标              | 机制                                                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **通道可替换**       | 服务端 `NotifyChannel` 接口（`send` / `capabilities` / `mapResult`）；采集端 `ReadChannel` / `SendChannel` 接口。**编排、落库、状态跟踪、前端均不感知具体通道** |
| 未来接入 R4（会话内容存档） | 新增 `ArchiveChannel` 实现 + 配置启用；**补齐** **`DELIVERED`** **采集点**（状态机已预留该状态）                                                      |
| 未来接入 T3（官方 CLI） | 新增 `CliChannel` 实现（进程外调用）；编排不变                                                                                               |
| **客户端改版隔离**     | A-L2 `ClientStructureAdapter` 承载全部控件定位规则（版本化规则集，服务端下发）；**改版只改规则，不改通道与编排**                                                    |
| 多采集端扩展          | 节点注册 + 心跳 + 配置按节点下发；任务按节点与驿站路由                                                                                               |

> `TODO(扩展): 当通道数 ≥3（Webhook + 仿人工 + CLI/存档）时，评估把「通道」与「目标类型（群/单聊）」拆为双维度注册表，避免实现组合爆炸。`

### 15.4 可观测性

| 类别   | 内容                                                                                     |
| ---- | -------------------------------------------------------------------------------------- |
| 日志分级 | `error` 记堆栈；`warn` 记可恢复（限频命中、重试）；`info` 记关键流转（任务状态推进）；`debug` 记排障。**不打印完整通知内容与敏感字段**   |
| 关键指标 | 心跳延迟、读取成功率、解析命中率（L1/L2/L3 分布）、提交成功率、近似送达率、失败率、死信率、限频命中次数、人工确认积压量、资源（memMb/handleCount） |
| 告警项  | 节点心跳连续 3 次缺失；结构突变；登录态失效；死信新增；人工确认积压超阈；限频命中持续升高；一键停用被触发                                 |
