**ARCH-S-1 `V22` 排班唯一键（关键）**
- 基线核验（成立）：`V5__attendance.sql:77-80` 与 `db.md:638-639` 均**仅两个普通索引、无 UNIQUE**；Service 查重键为 `(employeeId, workDate)`（`AttendanceScheduleService.java:13`、`findOne` `:370-379` 取首条）。
- **独立核验发现重大不符**：架构 §2.4（`:163`）与算法 §1.2（`:68`）均称删除语义为「**物理删**（`deleteById`，`:185`、`:332`）」。实测 `AttendanceSchedule.java:39-40` 的 `isDeleted` 标注 **`@TableLogic`**，且 `AttendanceScheduleMapper.java:9` 为裸 `BaseMapper`（无覆盖）→ `deleteById` 实为**逻辑删（UPDATE is_deleted=1）**，**非物理删**。
- 由此推论（直接影响结构正确性）：
  1. `UNIQUE (employee_id, work_date, shift_id)` **不含 `is_deleted`** 与 `@TableLogic` 逻辑删**互斥**：清空某班次（软删）后，同一 `(emp,date,shift)` 再插入 → 命中残留软删行 → **1062 唯一键冲突**，多班次「清空后再排」主流程会失败。这正是算法 T3（`:430`）登记的「软删与唯一键共存」，却被同时声明为「沿用物理删」→ **自相矛盾**，且被降格为 `TODO` 而非阻断项。
  2. 迁移「存量重复行查重预检（须返回 0 行）」（架构 `:166`、算法 §8-1 `:396`）**口径不完整**：普通 `UNIQUE` 索引包含 `is_deleted=1` 行，预检必须**含软删行**，否则预检通过后加键仍可能 1062 失败。
- 判定：**不完整、存在正确性缺陷 → 必改 M-1**。

### 核对 3 · 多班次与既有计薪口径的一致性（关键，独立核验）

**(a) 算法称「计薪侧已实现多班次（≤2/天）」——成立。**
- `ShiftPayrollPolicy.shiftUnit`（`:54-56`）= `workDate.toEpochDay() * 2L + ordinal`；`requiredShiftSet`（`:98-118`）按 `(workDate, shiftOrdinal)` 去重；`shiftOrdinal`（`:64-79`）按 `middayBoundaryMinute` 返回 0/1 → 「一天最多 2 个半天单元」**与实测一致**，算法 §0 FC1 成立。

**(b) `period_index` 与 `shiftOrdinal(start_time)` 的映射能否对齐——仅为「待落地约定」，非既成事实。**
- 实测：单班次模型下打卡记录写 `periodIndex = 0`、`periodName = periods.get(0).name()`（`AttendanceRecordServiceImpl.java:354-355`），且 `findSchedule`（`:531-538`）取首条 → 多班次下第二班次**无时间基准**（算法 FC7 成立）。
- 算法 §1.5（`:110-127`）要求「`period_index` := 班次 `ordinal`」，其前提是**不变式 A2**（`attendance_rule.check_periods` 顺序 ≡ `attendance_shift` 按 `start_time` 升序，算法 §7.1 `:373`、§8-8 `:403`）。该不变式**当前无任何强制校验**，仅靠「约定 + 降级告警」（算法 §9 `:417`）→ **序号漂移风险实质存在**，交实现时须落校验。见发现项 F-07。

**(c) `AttendanceSummaryPolicy` 缺卡误判——成立。**
- 实测 `AttendanceSummaryPolicy.summarize`（`:35-59`）：实到 = `actualIds.size()`（按 `employeeId` 去重，`:39,56`）、缺卡 = `Math.max(0, shouldCount - actualCount)`（`:57`）；`shouldCount = scheduleRows(stationId, workDate).size()`（`AttendanceRecordServiceImpl.java:151`，**排班行数**）→ 一天两班全勤时 `shouldCount=2`、`actualCount=1` → `absentCount=1`，**FC6 误判成立**。
- 该改动属**出勤/考核口径**（考勤概况/明细呈现），须用户裁定（用户 §三 A-① 仍待裁定）→ 本报告**不据此打回**，列为**放行前置**。

**(d) 唯一性键与「活跃唯一」语义自洽性——在「物理删」前提自洽；实测为逻辑删 → 不自洽。**
- 算法 §1.2（`:68`）选择物理删以「避免软删与唯一键互斥」；`employee.phone_active` 生成列手法（`db.md:215,226`、`V16` `:1492-1498`）是既有的「活跃唯一」范式（`UNIQUE(phone_active)`，`is_deleted=1` 行置 NULL）。多班次若要保留 `@TableLogic` 软删，**须改用同范式**（生成列/部分唯一/`is_deleted` 入键），不能只加裸三元 `UNIQUE`。见必改 M-1。

**(e) 新增风险：唯一序号 0/1 与「同半天两班」冲突（未登记）。**
- `shiftOrdinal`（`:64-79`）仅为早/晚二分；若同日两班次**均落在午前**（如 06:00–09:00 + 09:00–11:00，相邻不重叠、通过重叠校验），两者 `ordinal` **均为 0** → 计薪 `R` 去重后 `|R|=1` → 折算**少算**（与算法「多班次对计薪影响=0」结论相悖）。
- 算法 §7.1 假设 A1 仅覆盖「>2 班」与「=12:00 边界」，**未覆盖同半天双班**；架构 §2.4 校验清单（`:148`）亦**无「同日两班 ordinal 须互异」**。见必改 M-4 / 发现项 F-03。

## 三、新引入问题排查

### 3.1 生成列式唯一后的并发强度

- **结论：达到原裸唯一键强度。** 两并发插入同 `(employee_id, work_date, shift_id)` **活跃行**时，生成列 `active_shift_key` 取值相同 → `UNIQUE` 原子拒绝第二条（1062），与裸三元唯一键同强度；软删行生成列置 `NULL`（MySQL `UNIQUE` 允许多 `NULL`）→ 仅活跃行受限。依据：`V22:17-20,69-72`；算法 §1.2（`algorithm-multi-shift-scheduling.md:104`）、§6.1-N1/N9（`:432,440`）。**未运行验证（无 MySQL）→ 标「待核实」**，收敛服务器阶段（`algorithm-multi-shift-scheduling.md:463`）。

### 3.2 生成列对 `INSERT`/`UPDATE` 的影响（**实现约束**）

- **应用层不得显式赋值该列。** MyBatis-Plus 仅写入实体已声明字段；正确做法是实体 `AttendanceSchedule` **不声明** `active_shift_key`（对齐既有 `Employee` 未声明 `phone_active`，`V16` 同范式）——**无需** `@TableField(exist=false)`，只需不落字段；否则 MP 会尝试写生成列而报错。逻辑删（`deleteById` → `UPDATE is_deleted=1`）触发生成列自动重算为 `NULL`，无需应用干预。依据：算法 §1.2 落地边界第 2 点（`algorithm-multi-shift-scheduling.md:115`）。**该实现约束已在算法文档声明，但架构 §2.4 未复述** → 交实现任务时须携带（非方案缺陷，登记）。

### 3.3 审计表 16 列中 `operator_type`/`target_name`/`fail_reason` 的出处

| 列 | 架构 §3.2 是否定义 | 结论 |
| --- | --- | --- |
| `operator_type` | **是**（`boss-management-architecture.md:301`，`USER/SYSTEM`，对齐 `payroll_log`） | 与架构一致，**非自行增补** |

### 3.4 `action` 取值 `CHANGE_STATUS` 与架构/契约一致性

- **不一致。** 架构 §3.2/§3.3 的「启停」枚举名为 **`STATUS`**（`boss-management-architecture.md:304,325,332`）；`V23:38`、`init.sql:1007`、`db.md:1703` 均用 **`CHANGE_STATUS`**。`db.md:1736,1743` 已自述该差异并注明「按主代理指令」，但**本次复评基准（主代理裁定 A-②~A-⑥）未列明该指令**（出处 **待核实**）。→ 见 N-2。
