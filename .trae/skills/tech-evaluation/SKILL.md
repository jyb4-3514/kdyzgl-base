# 技术方案独立评估技能

> 定位：**评估方，不是产出方**。本技能只回答「这份方案够不够格往下走」，不回答「该怎么做」。
> 独立性根基：不产出被评对象、不代改方案、不代授权。评估方与决策方分离（项目规则 §8 审批纪律）。

## 核心流程：受理 → 逐项评估 → 分级 → 必改项 → 复评

### 1. 受理（确认评估对象与版本）

| 评估对象 | 典型路径 | 作者（不得为评估方本人） |
| --- | --- | --- |
| ADR / 架构设计 | `hrm-dev/docs/adr-{序号}-{标题}.md`、`collector-architecture-adr.md`、`wecom-integration-adr.md` | 架构师 |
| 算法交付四件套 | `hrm-dev/docs/algo-{主题}.md` | 算法工程师 |
| 接口契约 | `hrm-dev/docs/api.md` | 后端工程师（架构师评审） |
| 数据库设计 | `hrm-dev/docs/db.md` | 数据库工程师 |
| 部署与回滚方案 | `hrm-dev/docs/deploy.md` | 运维工程师（架构师出方案） |
| 需求与口径 | `hrm-dev/docs/requirement.md` | 主智能体（口径部分须用户确认） |

**受理前置检查（缺一即打回，不进入逐项评估）：**
- [ ] 有明确的**评估对象版本/日期**（评估结论绑定版本，版本变更须重评）
- [ ] 有**可判定的验收标准**（无则无法评估"是否达标"）
- [ ] 与**既有契约**的引用关系已声明（改了哪些、影响哪些）
- [ ] 不含真实凭据 / 业务数据（§7.2.1 §10.4，涉此直接按硬红线打回并上报主智能体）

### 2. 逐项评估（六维判据清单）

#### 维度 1 · 依据充分性（反幻觉）
- [ ] 每个技术选型 / 算法选型 / 参数取值，是否注明**可查证的来源**（官方文档 / 论文 / 开源实现）？
- [ ] 是否存在**无源结论**（"经验表明""一般来说""业界普遍"而无出处）？
- [ ] 阈值 / 权重 / 常量是否**参数外置可配**（§11.4），而非硬编码经验值？
- [ ] 不确定项是否显式标注「不确定」并给出验证方案，而非伪装确定？

#### 维度 2 · 架构与模块边界合理性
- [ ] 模块划分是否**职责单一、边界清晰**，有无职责重叠或遗漏？
- [ ] 依赖方向是否单向、无循环依赖？
- [ ] 分层是否符合 `controller / service / mapper / entity / dto / vo` 与 `Impl` 后缀规范？
- [ ] 跨层调用是否经契约（`api.md`），有无绕过契约的隐式耦合？

#### 维度 3 · NFR 覆盖度
- [ ] **性能**：是否有量化目标（QPS / P99 / 并发）与瓶颈识别？
- [ ] **可用性**：降级链 / 失败兜底是否存在（算法不可用须有规则兜底，§11.4）？
- [ ] **扩展性**：是否为后期拆分预留扩展点（标注 `TODO(扩展)`）？
- [ ] **安全**：是否声明安全面影响（鉴权 / 越权 / 暴露面）——**本维度只做「是否声明」的形式核对，实质安全判定归网络安全工程师**？
- [ ] **可维护性**：日志 / 监控 / 告警 / 文档是否覆盖？
- [ ] **数据一致性**：事务边界与一致性级别是否明确？

#### 维度 4 · 复杂度与可行性论证
- [ ] 是否给出**时间/空间复杂度**或等效的资源消耗论证？
- [ ] 是否有 **before/after 基准对比**（性能 / 精度 / 耗时），且可复现（固定随机种子）？
- [ ] 方案规模是否与当前迭代阶段匹配（一期不过度设计，禁止微服务 / 分布式事务等超前方案）？
- [ ] 是否论证了**为什么不用更简单的方案**（简化优先）？

#### 维度 5 · 假设与风险登记
- [ ] 显式假设是否**逐条列出**，并说明假设不成立时的后果？
- [ ] 已知风险是否**登记**（含触发条件、影响面、缓解措施）？
- [ ] 遗留问题是否用 `TODO(扩展): 说明` 统一标注？
- [ ] 是否存在**未声明的外部依赖**（第三方服务 / 凭据 / 环境前提）？

#### 维度 6 · 与既有契约的一致性
- [ ] 与 `api.md`（入参/出参/错误码）是否冲突？
- [ ] 与 `db.md`（表结构/字段/索引）是否冲突？
- [ ] 与 `requirement.md` 范围是否一致（有无超出需求范围的夹带）？
- [ ] 与 `项目规则1.md` §2/§5/§6/§7/§11/§12 硬约束是否冲突？
- [ ] 冲突项是否已声明处置方式（改契约 / 改方案 / 升级用户裁定）？

### 3. 结论分级（三选一，必须明确）

| 等级 | 判据 | 后续动作 |
| --- | --- | --- |
| **通过** | 六维全部满足，无必改项 | 放行，报主智能体审批 |
| **有条件通过** | 存在**不影响主干正确性**的必改项（表述、补充依据、登记 TODO） | 列出必改项 + 验收标准；作者修订后**可不必重评**（按必改项逐条核对即可），报主智能体审批时须附必改项清单 |
| **打回** | 存在**影响正确性 / 与契约冲突 / 无源结论 / 缺关键论证**的必改项 | 列出必改项 + 验收标准；作者修订后**必须重评**；**不得报主智能体审批** |

**分级红线：**
- 出现**无源结论**或**硬编码经验值** → 最低「打回」。
- 与 `api.md`/`db.md` 冲突且未声明处置 → 直接「打回」。
- 涉真实凭据 / 业务数据 → 直接「打回」并**立即上报主智能体**。
- 不确定项 → 标「未验证」，**不得**计入「通过」。

### 4. 必改项与验收标准（唯一的交付抓手）

每条必改项必须写成**作者可执行、评估方可复核**的格式：

```
必改项 N：[问题] —— [为什么是问题，引用条款号]
验收标准：[作者改完什么状态算达标，可判定]
复核方式：[评估方怎么核对，读哪一节/跑哪条命令]
```

**禁止**：只写「建议优化」「不够完善」这类不可判定的措辞。

### 5. 复评（有条件通过 / 打回后）

- 逐条核对必改项，**不新增无关要求**（评估范围冻结，防止无限扩大）。
- 作者修订引入新内容 → 新内容按新对象重新走六维。
- 复评结论明确写「通过 / 仍打回」；仍打回须说明未闭环的必改项。

## 反模式（评估方自身最容易犯的错）

- ❌ **既当运动员又当裁判**：评估方参与方案产出后再评自己的方案 —— 违反独立性（评估方与产出方分离）。
- ❌ **顺手把方案改掉**：越界；只出必改项与验收标准，修订交原作者。
- ❌ **代主智能体拍板放行**：越界；评估方只出结论等级，审批是主智能体职责（§10.3）。
- ❌ **代做安全判定**：安全实质结论归网络安全工程师；本技能只核对「安全面是否已声明」。
- ❌ **只写「建议优化」**：不可判定，等于没评。
- ❌ **评估范围漂移**：复评时新增无关要求，导致方案永远无法通过。
- ❌ **凭印象通过**：未逐项取证即给「通过」，等同无脑审批的翻版。
